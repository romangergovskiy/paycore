# План тестирования финансовых инвариантов

Статус: **принято для MVP** (этап 2). Инварианты I-01…I-13 описаны в [ledger-model.md §12](ledger-model.md#12-финансовые-инварианты), конкурентные сценарии S-01…S-28 — в [../database/concurrency.md §9](../database/concurrency.md#9-каталог-конкурентных-сценариев). Библиотеки — [D-38](decisions.md#d-38): `testing`, testcontainers-go, `pgregory.net/rapid`.

## 1. Стратегия

| Уровень | Что проверяет | Окружение | Когда запускается |
|---|---|---|---|
| Unit | Деньги, комиссии, машины состояний, валидация и построение проводок | Чистый Go, без БД | Каждый коммит |
| Property-based | Свойства арифметики и последовательностей операций | Go, in-memory модель + PostgreSQL | Каждый коммит (короткий прогон), nightly (длинный) |
| Integration | Ограничения, функции `ledger.*`, права ролей, триггеры, транзакционные шаблоны | Настоящий PostgreSQL той же версии, что в production, с ролями из [data-integrity.md §6](../database/data-integrity.md#6-роли-и-права-бд) | Каждый PR |
| Concurrency | S-01…S-28 под реальной конкуренцией | PostgreSQL + N горутин, `-race` | Каждый PR (короткий), nightly (много итераций) |
| Fault injection | Падения между шагами, обрыв соединения, падение relay и worker | PostgreSQL, прокси (toxiproxy) | Nightly / перед релизом |
| Invariant checker | Все I-xx на произвольном состоянии БД | SQL-запросы (REPEATABLE READ READ ONLY) | После каждого integration/concurrency-теста и по расписанию |
| Load (k6, ТЗ §7) | p95, повторы, ожидания блокировок, отсутствие нарушений инвариантов | Стенд | Этап Production Engineering |

Главный принцип: **любой тест, который меняет деньги, заканчивается проверкой инвариантов** (общий хелпер `assertLedgerInvariants(t, db)`), а не только проверкой ожидаемого результата.

Интеграционные и конкурентные тесты подключаются к БД **ролью `paycore_app`**, как приложение. Тесты, которым нужна запись в обход функций (проверка триггеров), явно переключаются на `paycore_owner`.

## 2. Invariant checker (переиспользуемый набор SQL)

Набор запросов, каждый из которых возвращает **пустой результат**, если инвариант выполняется. Используется в тестах, в фоновой задаче контроля и в отчёте Admin Dashboard. Большинство инвариантов уже гарантированы в момент записи ([ledger-model.md §12](ledger-model.md#12-финансовые-инварианты)); checker ловит ошибки в самих механизмах.

| Инвариант | Суть запроса |
|---|---|
| I-01 | Журналы, где по какой-либо валюте \(\sum D \ne \sum C\) или проводок меньше 2 |
| I-02 | Валюты, где глобально \(\sum D \ne \sum C\) |
| I-03 | Бизнес-счета, где `account_balances` ≠ пересчёт по проводкам AVAILABLE/HOLD; системные счета, где `SUM` бакетов ≠ пересчёт |
| I-04 | Проводки счетов с `allow_negative = false`, где `balance_after < 0`; бакеты с `balance < 0` |
| I-05 | Счета, где `reserved_amount` ≠ \(\sum\) ACTIVE-резервов ≠ баланс HOLD-счёта |
| I-06 | Платежи, где `refunded_amount` ≠ \(\sum\) `SUCCEEDED`-возвратов или > `captured_amount` |
| I-07 | Совпадение контрольной суммы проведённых записей со снимком, сделанным в начале теста (только в тестах) |
| I-08 | Объекты с несколькими «финальными» журналами (два `HOLD_CAPTURE`, `HOLD_CAPTURE` и `HOLD_RELEASE` у одного резерва) |
| I-09 | Разрывы цепочки: `balance_after(n) ≠ balance_after(n−1) ± amount(n)`; пропуски `account_version` |
| I-10 | Несогласованность статусов: `CAPTURED` без `HOLD_CAPTURE`; hold `ACTIVE` при `HOLD_RELEASE`; `FAILED`-перевод с журналом; `SUCCEEDED`-возврат без `REFUND`; `COMPLETED`-пополнение или выплата без журнала |
| I-11 | Проводки, где валюта ≠ валюте счёта (на случай снятого FK) |
| I-12 | Объекты, где `fee_amount` ≠ кредиту счёта дохода в журнале или ≠ пересчёту по `fee_tariff_id`; платежи, где `fee_amount ≥ amount` |
| I-13 | Проводки по бизнес-счёту, который на момент проводки был в статусе, запрещающем эту пару «операция + роль» ([ledger-model.md §11.4](ledger-model.md#114-статусы-счетов-и-допустимые-операции)); статус на момент проводки восстанавливается по `account_status_history` |

## 3. Unit-тесты

### 3.1. Деньги (`pkg/money`)

- Сложение и вычитание с переполнением возвращают ошибку: `MaxInt64 + 1`, `MinInt64 − 1`.
- Умножение на ставку на границе `MAX_AMOUNT × 10 000` ([D-35](decisions.md#d-35)).
- Сравнение сумм разных валют — ошибка, а не `false`.
- Парсинг строк: `"100.50"` (RUB) → 10 050; `"100.5"` → 10 050; `"100.505"` → ошибка (лишний знак); `"1e3"` → ошибка; валюта не из справочника → ошибка.
- Валюта, отличная от RUB, во входящем запросе (`USD`, `EUR`) → `422 CURRENCY_NOT_SUPPORTED` ([D-30](decisions.md#d-30)).
- Сериализация в JSON — только целые числа, без float.

| 500 000 | 150 bp | 7 500 | обычный расчёт |
| 100 000 | 150 bp | 1 500 | пример сквозного сценария |
| 30 000 000 | 50 bp, max 50 000 | 50 000 | срабатывание max |
| 333 | 150 bp, HALF_UP, min 0 | 5 | округление 4,995 → 5 |

Также проверяется выбор тарифа по `valid_from`/`valid_to` и персональный тариф магазина поверх базового.

### 3.3. Машины состояний

Табличный тест **всех пар** (статус × команда) для платежа, checkout-сессии, перевода, резерва, возврата и выплаты. Разрешённые переходы ([money-flows.md §2](money-flows.md#2-машины-состояний-mvp)) дают ожидаемый новый статус. Все остальные — доменную ошибку `INVALID_STATE`. Отдельно:

- статуса `PENDING` нет: подтверждение checkout ведёт `CREATED → AUTHORIZED` или `CREATED → FAILED` ([D-21](decisions.md#d-21));
- `CREATED → CANCELLED` по отмене магазином и истечению checkout;
- `AUTHORIZED → CANCELLED` по void и истечению авторизации;
- возврат из `CREATED`/`AUTHORIZED`/`FAILED`/`CANCELLED` невозможен (ТЗ §2.4 «нельзя вернуть средства по платежу, который не был проведён»);
- `PARTIALLY_REFUNDED → PARTIALLY_REFUNDED` и `→ REFUNDED` по сумме.

### 3.4. Валидация проводок (`Ledger.Post` без БД)

Отклоняются: < 2 проводок; сумма ≤ 0 или > MAX; несбалансированный журнал; несбалансированность в одной из двух валют при общем балансе (вторая валюта — тестовая фикстура справочника, в MVP только RUB, [D-30](decisions.md#d-30)); валюта проводки ≠ валюте счёта; дубль счёта в журнале; неизвестный `operation`; недопустимое сочетание операции и действия над резервом. Принимается корректный журнал из 2, 3 и 4 проводок.

### 3.5. Построители проводок (posting builders)

Для каждого сценария [money-flows.md](money-flows.md) — тест, что builder строит ровно ту таблицу проводок, что описана в документе. Документ и тест должны совпадать. Обязательные примеры:

- перевод своим счетам и другому клиенту (§4);
- `HOLD_CAPTURE` 500 000 → 492 500 + 7 500 (§5);
- полный возврат при MA = 592 500 и частичные R1–R4 (§7);
- `SIM_TOPUP` и `PAYOUT` (§3, §9).

### 3.6. Сквозной сценарий симулятора

Таблица [money-flows.md §8](money-flows.md#8-сквозной-сценарий-симулятора) исполняется как один тест через настоящие use case. После **каждого** шага сверяются остатки 1100, A1, A2, MA, 4200 с таблицей, а также «баланс баланса» ([chart-of-accounts.md §5](chart-of-accounts.md#5-проверка-баланса-баланса)). Шаг 7 обязан дать `FAILED (MERCHANT_INSUFFICIENT_FUNDS)` без проводок. Итог должен совпасть с [chart-of-accounts.md §6](chart-of-accounts.md#6-пример-состояние-после-сквозного-сценария).

### 3.7. Матрица статусов счёта

Табличный тест по [ledger-model.md §11.4](ledger-model.md#114-статусы-счетов-и-допустимые-операции): каждая строка «операция + роль» × статус `ACTIVE` / `BLOCKED` / `CLOSED`. Каждая комбинация проверяется **дважды**:

1. Через use case: разрешённая — успех; запрещённая — доменный отказ `ACCOUNT_NOT_ACTIVE` (объект `FAILED` или `409`, без проводок).
2. Прямым вызовом `ledger.post_journal` ролью `paycore_app` после взятия L3: разрешённая — журнал проведён; запрещённая — `PC403`, в БД ничего не появилось. Так проверяется, что функция не полагается на use case.

Обязательные комбинации:

| Комбинация | Ожидание |
|---|---|
| `TRANSFER`, отправитель `BLOCKED` | запрещено |
| `TRANSFER`, получатель `BLOCKED` | запрещено |
| `SIM_TOPUP` на `BLOCKED` | запрещено |
| `HOLD_PLACE`, покупатель `BLOCKED` | запрещено |
| Подтверждение checkout, магазин `BLOCKED` | запрещено (только use case: счёт магазина не в проводках) |
| `HOLD_CAPTURE`, покупатель или магазин `BLOCKED` | запрещено; платёж остаётся `AUTHORIZED`, резерв `ACTIVE` |
| `HOLD_RELEASE` (void, истечение), покупатель `BLOCKED` | разрешено; повторный void → `409 INVALID_STATE`, повторное освобождение функцией → `PC409` |
| `HOLD_RELEASE` с проводкой на другой бизнес-счёт (собранный вручную журнал) | `PC400` / `PC409`: исключение не распространяется на чужой счёт |
| `REFUND`, покупатель `BLOCKED`, магазин `ACTIVE` | разрешено; сумма ≤ `captured − refunded` |
| `REFUND`, магазин `BLOCKED` | запрещено |
| `PAYOUT`, магазин `BLOCKED` | запрещено |
| `REVERSAL` / `ADJUSTMENT` на `BLOCKED` по утверждённой заявке | разрешено; без заявки → `PC403` |
| Любая операция с `CLOSED`-счётом | запрещено, включая `REFUND` на счёт покупателя и `ADJUSTMENT` |
| Закрытие `ACTIVE` или `BLOCKED` с нулевыми `available` и `reserved` | разрешено; с ненулевыми → `409 ACCOUNT_NOT_EMPTY` |
| `CLOSED → ACTIVE`, `CLOSED → BLOCKED` | `409 INVALID_STATE` |

Для разрешённых исключений дополнительно проверяется, что бухгалтерские проверки не ослаблены: `REFUND` сверх остатка магазина → `PC402`; `HOLD_RELEASE` резерва не в `ACTIVE` → `PC409`.

## 4. Property-based тесты

Инструмент — `pgregory.net/rapid` ([D-38](decisions.md#d-38)).

### 4.1. Свойства арифметики и комиссий

- Для любых `amount ∈ [1, MAX]` и тарифа: `min ≤ fee ≤ max`; `fee ≥ 0`; результат детерминирован и целочисленный.
- Для любого capture: либо `fee < amount` и магазин получает `amount − fee ≥ 1`, либо `FEE_EXCEEDS_PAYMENT` без проводок; урезания комиссии до `amount` нет.
- Монотонность: `a ≤ b ⇒ fee(a) ≤ fee(b)` при одном тарифе.
- Для любого разбиения суммы платежа на возвраты: покупатель получает ровно \(\sum\) возвратов, доход 4200 по платежу не меняется ([D-09](decisions.md#d-09)).

### 4.2. Модельное тестирование (model-based / stateful)

- **Модель** — простая in-memory реализация «счета, резервы, платежи, лимиты», заведомо корректная (map и целые числа, без конкурентности).
- **Генератор** — случайные последовательности команд: тестовое пополнение, перевод (свой / чужой), создание платежа, подтверждение checkout, capture, void, истечение checkout и авторизации, частичный и полный возврат, выплата, блокировка и разблокировка счёта, повтор команды с тем же `Idempotency-Key` и тем же или другим телом, сдвиг времени через границу суток.
- Каждая команда применяется к **системе** (настоящие use case + PostgreSQL) и к **модели**. После каждого шага:
  - результаты совпадают (успех или ошибка того же кода);
  - балансы всех счетов, включая системные, совпадают с моделью;
  - invariant checker (§2) пуст.
- При падении фреймворк уменьшает (shrink) последовательность до минимальной воспроизводимой.
- Это реализует ТЗ §10: «тесты, проверяющие инварианты на случайных последовательностях финансовых операций».

### 4.3. Свойство «сохранения денег»

Для любой последовательности операций: баланс 1100 = \(\sum\) обязательств перед клиентами и магазинами (2100 + 2110 + 2200) + доход (4100 + 4200) − расходы (5900). Без `SIM_TOPUP`, `PAYOUT` и `ADJUSTMENT` баланс 1100 не меняется.

## 5. Конкурентные тесты

Общий каркас:

1. Подготовить состояние (fixture) в настоящей БД.
2. Запустить N горутин, синхронизированных барьером (закрытие канала-старта), чтобы запросы действительно пересекались.
3. Собрать результаты: коды ответов, итоговые статусы.
4. Проверить ожидаемый исход сценария **и** invariant checker.
5. Повторить M раз (100 в PR, 10 000 nightly), потому что гонки проявляются вероятностно.
6. Запуск с `go test -race`.

Нумерация совпадает с [concurrency.md §9](../database/concurrency.md#9-каталог-конкурентных-сценариев).

| Тест | Конфигурация | Проверка |
|---|---|---|
| S-01 | Баланс 1 000 000, 2…50 горутин по 800 000 | Ровно один `COMPLETED`; `available ≥ 0` |
| S-01-stress | Баланс 1 000 000, 100 горутин по случайным суммам | \(\sum\) успешных списаний с комиссией ≤ 1 000 000; итоговый баланс = 1 000 000 − \(\sum\) |
| S-02 | Встречные переводы и цикл A→B→C→A, много горутин | Нет `40P01`; деньги сохранены |
| S-03 | 10 горутин capture одного платежа с разными ключами | Один `HOLD_CAPTURE`; остальные `409 INVALID_STATE` |
| S-04, S-05 | capture × void, capture × истечение авторизации | Ровно один финальный журнал; статус резерва согласован |
| S-06 | 10 горутин частичных возвратов, в сумме больше `captured` | \(\sum\) успешных ≤ `captured` |
| S-07 | Возвраты разных платежей одного магазина при остатке на один | Один `SUCCEEDED`, остальные `MERCHANT_INSUFFICIENT_FUNDS`; MA ≥ 0 |
| S-08 | Переводы × подтверждения checkout с одного счёта | `available ≥ 0`, I-05 |
| S-09 | Перевод или платёж × блокировка счёта | Нет проведённой операции после коммита блокировки; I-13 |
| S-10, S-11 | Параллельные переводы с разных счетов одного пользователя против суточного лимита, в том числе первый запрос дня | \(\sum\) ≤ лимита; ровно одна строка счётчика |
| S-12 | 20 горутин с одним ключом и одним телом | Одна операция, 20 одинаковых ответов |
| S-13 | Один ключ, разные тела, одновременно | Одна операция; остальные `409 IDEMPOTENCY_KEY_REUSED` |
| S-14, S-15 | Потеря ответа на `COMMIT`; падение до `COMMIT` | Повтор с ключом даёт ровно одну операцию |
| S-16 | Kill relay между захватом и подтверждением | После истечения lease событие опубликовано повторно; эффект у потребителя один |
| S-17 | 3 экземпляра relay | Пачки не пересекаются; порядок `seq` внутри агрегата сохранён |
| S-18 | Повторная доставка события потребителю | Эффект ровно один (inbox) |
| S-19 | Kill scheduler во время истечения резервов | Каждый резерв освобождён ровно один раз |
| S-20 | 100 горутин capture разных магазинов | Ни одной ошибки блокировки; `SUM` бакетов 4200 = пересчёт; нагрузка распределена по бакетам |
| S-21 | Выплаты × пополнения | Нет `40P01`; каждый бакет 1100 ≥ 0 |
| S-22 | Смена тарифа во время capture, в том числе на тариф с `min ≥ amount` | `fee_tariff_id` указывает на одну версию; I-12; при `FEE_EXCEEDS_PAYMENT` платёж `AUTHORIZED`, резерв `ACTIVE`, журнала нет |
| S-23 | Чтение остатка с реплики | Статическая проверка: все денежные use case читают остатки только через `lock_account_balances` |
| S-24 | Закрытие счёта × подтверждение checkout; закрытие при активном резерве | Либо закрытие `409 ACCOUNT_NOT_EMPTY`, либо подтверждение `ACCOUNT_NOT_ACTIVE`; при резерве — всегда `409 ACCOUNT_NOT_EMPTY`; нет `40P01` |
| S-25 | Блокировка покупателя × void и × истечение резерва | Резерв освобождён ровно один раз; I-05, I-08 |
| S-26 | Блокировка покупателя × возврат; блокировка магазина × возврат | Покупатель `BLOCKED` — `SUCCEEDED`; магазин `BLOCKED` — `FAILED (ACCOUNT_NOT_ACTIVE)` без журнала |
| S-27 | Блокировка магазина × capture | Capture до блокировки или `422 ACCOUNT_NOT_ACTIVE`; I-13 |
| S-28 | Прямой вызов `post_journal` без L3 при параллельной смене статуса | `PC460`, ничего не проведено |

Проверка порядка L1–L8: в тестовой сборке обёртка транзакции записывает последовательность захваченных уровней (хук в репозиториях и функциях `ledger.*`). Тест прогоняет все use case и проверяет, что уровни не убывают и что ни одна операция L8 (вставка или обновление) не выполнена раньше последнего захвата L2–L7 той же транзакции ([concurrency.md §3](../database/concurrency.md#3-единый-порядок-захвата-блокировок)). Повторное обращение к строке, уже заблокированной на более раннем уровне, новой блокировкой не считается.

Дополнительно — тест-«детектор deadlock»: случайная смесь всех use case, включая выплаты и корректировки, с проверкой, что `40P01` не возникает ни разу. Его появление — баг в порядке блокировок, а не повод для повтора.

## 6. Интеграционные тесты БД

### 6.1. Права и функция-шлюз

Подключение ролью `paycore_app` ([D-03](decisions.md#d-03), [D-33](decisions.md#d-33)):

- `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` на `journal_transactions`, `ledger_entries`, `account_balances`, `system_balance_buckets`, `holds` → `permission denied`.
- `SELECT … FOR UPDATE` на `account_balances` → `permission denied`; `ledger.lock_account_balances` работает и возвращает строки в порядке `account_id` при любом порядке аргументов.
- `ledger.post_journal`:
  - журнал из 1 проводки, несбалансированный, с суммой 0 или > MAX, с чужой валютой → `PC400`, в БД ничего не появилось;
  - списание сверх остатка бизнес-счёта → `PC402`;
  - уменьшение системного счёта сверх `SUM` бакетов → `PC402` (`SYSTEM_ACCOUNT_INSUFFICIENT`);
  - проводка по системному ledger-счёту не в `ACTIVE` → `PC403`;
  - запрещённая матрицей комбинация «операция + роль + статус» бизнес-счёта → `PC403` (полный набор — §3.7);
  - строка `accounts.accounts` удерживается чужой сменой статуса (`FOR NO KEY UPDATE` в другой сессии) → `PC460` сразу, без ожидания (`FOR SHARE NOWAIT`);
  - повтор того же бизнес-ключа с теми же проводками → существующий журнал, `already_posted`, новых строк нет;
  - тот же бизнес-ключ с другими проводками → `PC409`;
  - `CAPTURE` резерва не в `ACTIVE` → `PC409`.
- Нет способа добавить проводку в существующий журнал: у `paycore_app` нет `INSERT`, а функция всегда создаёт новый журнал.
- Функции имеют `search_path = pg_catalog, ledger`; `EXECUTE` отозван у `PUBLIC`.

### 6.2. Триггеры и ограничения

Каждое — отдельный тест «нарушить напрямую через SQL под `paycore_owner` → ожидать ошибку с именем ограничения»:

- `UPDATE` / `DELETE` / `TRUNCATE` на `ledger_entries`, `journal_transactions`, `*_status_history`, `audit_logs` → ошибка триггера (ТЗ §10 «Изменение проведённой проводки — запрещено»).
- Журнал без проводок → ошибка на `COMMIT` (отложенный `trg_journal_balanced`).
- Несбалансированный журнал из нескольких `INSERT` → ошибка на `COMMIT`; сбалансированный → успех.
- `amount = 0`, `amount < 0`, `amount > MAX` в проводке.
- Проводка в валюте, отличной от валюты счёта (составной FK).
- `available_amount < 0`, `reserved_amount < 0`, бакет `< 0` при `allow_negative = false` → `check_violation`.
- Повторный журнал с тем же `(reference_type, reference_id, operation, operation_seq)` → `unique_violation`; двойное сторно.
- Дубль `(ledger_account_id, account_version)`.
- Пересечение периодов тарифов и правил лимитов (EXCLUDE).
- Перевод между счетами разных валют; перевод самому себе.
- `refunded_amount > captured_amount`; `fee_amount >= amount` (CHECK `fee_amount < amount`).
- `payments.status = 'PENDING'` → `check_violation`.
- `approved_by = created_by` в `manual_adjustments`.

### 6.3. Идемпотентность

Все 12 случаев [concurrency.md §4.3](../database/concurrency.md#43-поведение-второго-запроса) — отдельные тесты. Ключевые:

- одновременные запросы с одним ключом: второй ждёт и возвращает сохранённый ответ (заголовок `Idempotent-Replayed`);
- первый откатился — второй выполняет операцию сам;
- ожидание дольше `lock_timeout` → `409 REQUEST_IN_PROGRESS`;
- другое тело → `409 IDEMPOTENCY_KEY_REUSED`, независимо от порядка;
- бизнес-отказ `422` сохраняется и повторяется, даже если деньги появились;
- ключ удалён очисткой → повтор упирается в бизнес-`UNIQUE` и не создаёт вторую операцию;
- `IN_PROGRESS` никогда не виден другой сессии закоммиченным (проверка из второго соединения во время операции).

### 6.4. Outbox и inbox

- Событие появляется только при коммите бизнес-транзакции; при откате его нет.
- Захват пачки — короткая транзакция: после неё нет удерживаемых блокировок (`pg_locks` пуст для сессии relay).
- Подтверждение чужого или просроченного lease обновляет 0 строк.
- Событие агрегата не захватывается, пока более раннее событие того же агрегата в `PENDING`.
- После `max_attempts` → `DEAD`, алерт; более поздние события агрегата продолжают публиковаться.
- Webhook worker: тот же набор тестов на `webhook_deliveries`.

### 6.5. Транзакционные шаблоны

- Каждый use case из [concurrency.md §5](../database/concurrency.md#5-шаблоны-транзакций): успешный путь создаёт ровно ожидаемые журналы, проводки, историю статусов, outbox-событие и запись idempotency **в одном коммите**. Инъекция ошибки на последнем шаге: после неё в БД нет ни одного следа операции.
- Отказ из-за бизнес-правила сохраняет объект `FAILED` без проводок ([D-19](decisions.md#d-19)).
- Retry-обёртка: искусственный `40001`/`40P01` на первой попытке → успех на второй, эффект один.
- Счёт `BLOCKED`: перевод, подтверждение checkout, capture, выплата отклоняются; void, истечение и возврат на счёт покупателя проходят ([D-26](decisions.md#d-26)). Полная матрица — §3.7.
- Capture с `FEE_EXCEEDS_PAYMENT`: ответ `422` сохранён в ключе идемпотентности; повтор с тем же ключом возвращает тот же `422`, даже если тариф вернули; повтор с новым ключом проходит по действующему тарифу; void после отказа проходит ([D-27](decisions.md#d-27)).
- Выплата при нехватке бакетов 1100 (искусственно уменьшенный 1100 под `paycore_owner`): `PC402` внутри `SAVEPOINT sp_payout` → объект выплаты `FAILED (PAYOUT_SOURCE_INSUFFICIENT)` закоммичен, проводок нет, остаток магазина не изменился.
- Лимит: void в тот же день возвращает лимит, на следующий день — нет; возврат лимит не возвращает ([D-24](decisions.md#d-24)).

### 6.6. Восстановление баланса

Заполнить БД случайными операциями (§4.2) → обнулить проекции и бакеты в тестовой БД под `paycore_owner` → пересчитать из ledger → совпадение с исходными значениями (ТЗ §2.3 «восстановление баланса по истории»).

## 7. Fault injection

| Сбой | Ожидание |
|---|---|
| Kill процесса после `COMMIT`, до ответа клиенту | Повтор с ключом возвращает результат, эффект один |
| Kill процесса до `COMMIT` | Транзакция откатилась, ключа нет; повтор выполняет операцию один раз |
| Обрыв соединения во время `COMMIT` (прокси) | Исход определяется повтором с тем же ключом |
| Зависшая сессия без закрытия TCP | `idle_in_transaction_session_timeout` завершает её; блокировки сняты |
| Обработчики outbox недоступны N минут | События копятся в `PENDING`, после восстановления все доставлены (ТЗ §10 «падение Kafka» — в MVP аналог без Kafka) |
| Kill relay после публикации, до подтверждения | Дубль события, потребитель отбрасывает его через inbox |
| Kill webhook worker во время HTTP-вызова | После истечения lease доставка повторяется; магазин дедуплицирует по `PayCore-Event-Id` |
| `lock_timeout` из-за длинной чужой транзакции | `503` + `Retry-After` (или `409 REQUEST_IN_PROGRESS` для ключа), без частичных эффектов |
