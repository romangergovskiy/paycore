# Спорные решения, открытые вопросы и допущения

Это единый реестр того, что требует согласования. Пока решение не согласовано, проектные документы используют **рекомендованный** вариант. После согласования решения оформляются как ADR в `docs/adr/` (ТЗ §11).

Статус всех решений ниже — «предложено, ждёт согласования».

---

## 1. Спорные решения

### D-01
**Резервирование: проводки в ledger или только «memo»-резерв.**
- **A.** Резерв — журнал `HOLD_PLACE` (Дт 2100 / Кт 2110). `reserved_amount` восстанавливается из ledger. *Плюсы:* единый первоисточник, ТЗ §2.3 «восстановление баланса по истории», «поддержка резервирования в Ledger». *Минусы:* в 2 раза больше журналов на платёж.
- **B.** Резерв — только строка `holds` и поле `reserved_amount`, проводки создаются при capture. Так поступают многие банки (авторизация — не проводка). *Плюсы:* меньше записей. *Минусы:* резерв не виден в ledger, «доступный остаток» не доказуем по истории.
- **Рекомендация: A.**

### D-02
**Проекции балансов системных счетов.**
- **A.** Синхронная проекция только у клиентских и мерчантских счетов. Системные счета считаются агрегатом или по снапшотам. *Плюсы:* нет горячей строки «Доход от комиссий». *Минусы:* нельзя мгновенно запретить отрицательный остаток системного счёта (контролирует задача сверки).
- **B.** Проекция у всех счетов. *Минусы:* все платежи сериализуются на одной строке.
- **C.** Проекция у системных счетов, шардированная на N строк.
- **Рекомендация: A**, а C — если понадобится онлайн-баланс системных счетов.

### D-03
**Где обеспечивать сбалансированность журнала.**
- **A.** Go-сервис `Ledger.Post` (основная проверка) + отложенный constraint trigger в БД (страховка) + запрет UPDATE/DELETE.
- **B.** Только SQL-функция `ledger.post_journal(jsonb)` с `SECURITY DEFINER`; у приложения нет прямого `INSERT`. *Плюсы:* гарантия на уровне БД без триггеров. *Минусы:* логика в PL/pgSQL, хуже тестируется из Go, больше работы при выделении сервиса.
- **C.** Только Go. *Минусы:* ручной SQL или баг обходят проверку.
- **Рекомендация: A.**

### D-04
**Уровень изоляции для денежных операций.**
- **A.** READ COMMITTED + `FOR UPDATE`/`FOR SHARE` в фиксированном порядке + условные UPDATE + CHECK.
- **B.** SERIALIZABLE везде + retry. *Плюсы:* корректность без ручных блокировок. *Минусы:* много откатов на горячих счетах, менее предсказуемо.
- **C.** Оптимистичные `version` без блокировок. *Минусы:* шторм повторов при конкуренции.
- **Рекомендация: A**, retry на 40001/40P01 реализуется в любом случае. REPEATABLE READ READ ONLY — для отчётов и проверок.

### D-05
**Перевод: прямое проведение или всегда через резерв.**
- **A.** `ALLOW` — один журнал `TRANSFER`; `REVIEW` — `HOLD_PLACE`, затем `HOLD_CAPTURE` или `HOLD_RELEASE`. Отменить можно только `ON_HOLD`.
- **B.** Всегда через резерв (2 журнала). *Плюсы:* один путь кода, отмена возможна всегда до capture. *Минусы:* вдвое больше записей, а «отмена до проведения» на практике бессмысленна при мгновенном capture.
- **C.** Всегда прямое проведение, `REVIEW` без резерва. *Минусы:* за время проверки клиент может потратить деньги.
- **Рекомендация: A.**

### D-06
**Статус журнала.**
- **A.** Журнал создаётся только проведённым (`status = 'POSTED'`, CHECK). Отмена — новым журналом.
- **B.** Жизненный цикл `PENDING → POSTED/VOIDED` у журнала. *Минусы:* противоречит неизменяемости; «pending»-движения уже моделируются резервами.
- **Рекомендация: A.** Колонка `status` сохраняется ради совместимости с ТЗ и для будущих сценариев (если нужны). Иначе её можно удалить.

### D-07
**Идемпотентность.**
- **A.** Два уровня: HTTP (`idempotency_keys` в той же транзакции, хеш тела, сохранённый ответ) + бизнес-`UNIQUE` (платежи, переводы, возвраты, ledger).
- **B.** Только `payments.idempotency_key` и аналоги в доменных таблицах. *Минусы:* нет повтора исходного ответа, нет проверки тела, а внутренние шаги (capture) не защищены.
- **Рекомендация: A.**

### D-08
**Комиссия за платёж.**
- **A.** Удерживается с мерчанта в журнале capture (мерчант получает `amount − fee`).
- **B.** Списывается с мерчанта отдельно при выплате или периодически (invoice). *Минусы:* мерчант видит «грязную» сумму, возможна задолженность.
- **C.** Платит клиент сверх суммы. Нетипично для эквайринга.
- **Рекомендация: A.**

### D-09
**Комиссия при возврате.**
- **A.** Не возвращается мерчанту (так поступает, например, Stripe). Полный возврат стоит мерчанту `fee`.
- **B.** Возвращается пропорционально через контр-счёт 4900.
- **Рекомендация: A для MVP**, архитектура (поля `fee_refund_amount`, `refunded_fee_amount`, счёт 4900) допускает B без миграции модели.

### D-10
**Возврат при недостатке средств у мерчанта.**
- **A.** Отказ (`MERCHANT_INSUFFICIENT_FUNDS`).
- **B.** Проводится, недостача — задолженность мерчанта (счёт 1300).
- **C.** Rolling reserve на счёте 2210.
- **Рекомендация: A для MVP.**

### D-11
**Владелец бизнес-счёта.**
- **A.** Две nullable-колонки `user_id` и `merchant_id` с FK и `CHECK num_nonnulls = 1`.
- **B.** `owner_type` + `owner_id` (полиморфно, без FK).
- **Рекомендация: A** (целостность через FK).

### D-12
**FK между модулями в монолите.**
- **A.** Разрешены по явному списку ([er-diagram.md §6](../database/er-diagram.md#6-межмодульные-связи)), удаляются при выделении сервисов.
- **B.** Запрещены полностью (только id). *Минусы:* теряется целостность уже сейчас.
- **Рекомендация: A.**

### D-13
**Перечисления в БД.**
- **A.** `TEXT + CHECK`. Изменение — `ALTER ... DROP/ADD CONSTRAINT` в миграции.
- **B.** `CREATE TYPE ... AS ENUM`. Значение нельзя удалить, добавление в транзакции ограничено.
- **C.** Справочные таблицы с FK.
- **Рекомендация: A**, C — для плана счетов (`chart_of_accounts`) и ролей.

### D-14
**Идентификаторы.**
- **A.** UUIDv7, генерируется в Go. Время в префиксе даёт локальность B-tree, а id известен до `INSERT` (нужен для `reference_id`).
- **B.** UUIDv4 (`gen_random_uuid()`). **C.** `BIGINT IDENTITY` (не соответствует ТЗ, раскрывает объёмы).
- **Рекомендация: A.**

### D-15
**Источник тестовых денег.**
- **A.** Пополнение из симулированного банка: Дт 1100 / Кт 2100.
- **B.** Демо-эмиссия: Дт 3100 Капитал / Кт 2100. Проще, но экономически бессмысленно (капитал «отрицательный»).
- **Рекомендация: A.**

### D-16
**Running balance в проводках (`account_version`, `balance_after`).**
- **A.** Хранить для счетов с проекцией. `UNIQUE (ledger_account_id, account_version)`. *Плюсы:* выписка и остаток на дату без агрегатов, детект потерянных обновлений, проверка I-09. *Минусы:* строгая сериализация на счёте (уже есть из-за `FOR UPDATE`), сложнее шардировать.
- **B.** Не хранить, считать агрегатом.
- **Рекомендация: A.**

### D-17
**Округление комиссий и единица ставки.**
- **Варианты округления:** `HALF_UP` (интуитивно), `HALF_EVEN` (банковское, без систематического смещения), `UP` (в пользу платформы).
- **Единица ставки:** базисные пункты (0,01 %) или ppm (0,0001 %).
- **Рекомендация:** `HALF_UP`, ставка в bp. Режим округления хранится в тарифе, чтобы его можно было сменить без кода.

### D-18
**Схемы PostgreSQL по модулям.**
- **A.** Отдельная схема на модуль, отдельные права. Подготовка к разделению данных (ТЗ §3.3).
- **B.** Всё в `public`.
- **Рекомендация: A.**

### D-19
**Сохранять ли отклонённые операции.**
- **A.** Бизнес-отказы сохраняются со статусом `FAILED` и кодом (нужно для аудита, фрод-правила «неудачные попытки», отчёта «успешные и неуспешные», ТЗ §2.11).
- **B.** Только HTTP-ошибка без сохранения.
- **Рекомендация: A.** Ошибки валидации формата не сохраняются.

## 2. Вопросы для согласования

<a id="q-01"></a>**Q-01.** Кто создаёт и кто авторизует платёж? Рекомендация: мерчант создаёт (API-ключ, без счёта клиента), клиент авторизует своим токеном с выбором счёта. Верно ли, что мерчант **не может** указать счёт клиента?

<a id="q-02"></a>**Q-02.** Утверждаете ли машину состояний платежа ([money-flows.md §2.1](money-flows.md#21-платёж))? Что такое `PENDING` в ТЗ? Может ли клиент сам отменить авторизацию? Повторяема ли авторизация после `FAILED`? Нужен ли отдельный статус `EXPIRED`?

<a id="q-03"></a>**Q-03.** Есть ли в MVP платежи через внешнего провайдера (карта-симулятор), или провайдер нужен только для сверки? Если есть — берёт ли симулятор комиссию?

<a id="q-04"></a>**Q-04.** Как пополняется счёт: кнопка «тестовое пополнение» у клиента, только администратор или скрипт сидирования? Нужен ли вывод средств клиентом?

<a id="q-05"></a>**Q-05.** Срок жизни авторизации (предложение — 7 суток, настраиваемо) и срок оплаты созданного платежа (предложение — 24 часа)?

<a id="q-06"></a>**Q-06.** Нужны ли частичный capture и несколько capture по одному платежу? (В MVP предложено — нет.)

<a id="q-07"></a>**Q-07.** Модель выплат мерчанту: вручную или по расписанию, синхронно или асинхронно, задержка расчётов (T+N), комиссия за выплату? Один счёт мерчанта на валюту или на магазин?

<a id="q-08"></a>**Q-08.** Список валют MVP (предложение: RUB, USD, EUR)? Нужен ли FX хоть в каком-то виде?

<a id="q-09"></a>**Q-09.** Комиссии:
- (а) платит ли отправитель перевода сверх суммы или из суммы;
- (б) есть ли комиссия за переводы между своими счетами (предложение — 0);
- (в) min/max задаются для каждой валюты;
- (г) что делать, если min-комиссия больше суммы платежа (ограничить `fee ≤ amount` или запретить такие платежи);
- (д) фиксировать комиссию платежа при авторизации или при capture.

<a id="q-10"></a>**Q-10.** Идемпотентность: TTL ключа (предложение — 24 ч, как у Stripe), область уникальности (пользователь, мерчант или API-ключ), код при несовпадении тела — `409` (как в ТЗ «конфликт») или `422`?

<a id="q-11"></a>**Q-11.** Максимальная сумма одной операции и баланса (предложение — \(10^{14}\) минорных единиц или бизнес-лимит меньше)?

<a id="q-12"></a>**Q-12.** Модель лимитов: какие лимиты (на операцию, сутки, месяц), на что (счёт, пользователь, мерчант), кто меняет (ADMIN с аудитом)? От ответа зависит, нужна ли блокировка счётчика лимита (S-20).

<a id="q-13"></a>**Q-13.** Закрытие счёта: разрешено ли с ненулевым остатком или с активными резервами (предложение — нет)? Формат номера счёта (предложение — 20 цифр в стиле РФ, без претензии на реальный БИК, или префикс `PC` + цифры с контрольной суммой)?

<a id="q-14"></a>**Q-14.** Семантика блокировки: запрещены ли зачисления на заблокированный счёт; возвраты на него; capture уже авторизованных платежей; нужен ли отдельный механизм «ограничение операций» (дебет/кредит) помимо статуса?

<a id="q-15"></a>**Q-15.** Ручные корректировки: кто инициирует и кто утверждает (OPERATOR → ADMIN?), есть ли пороги суммы для второго утверждения, нужно ли обоснование со ссылкой на инцидент?

<a id="q-16"></a>**Q-16.** Fraud `REVIEW`: срок разбора и решение по истечении (отклонить или одобрить); допустима ли неточность velocity-правил при гонке; подразумевает ли «отмена перевода до проведения» отложенные (scheduled) переводы?

<a id="q-17"></a>**Q-17.** Учётный часовой пояс и учётная дата (UTC или Europe/Moscow), границы дня для выписок и отчётов?

<a id="q-18"></a>**Q-18.** Нужен ли когда-либо овердрафт (отрицательный доступный остаток клиента)? Предложение — нет.

<a id="q-19"></a>**Q-19.** Сверка: формат реестра симулятора (CSV/JSON), ключ сопоставления (`provider_reference`), допустимые расхождения, кто разбирает и какими действиями (корректировка, игнор)?

<a id="q-20"></a>**Q-20.** Audit log: достаточно ли append-only с правами БД, или нужна хеш-цепочка (tamper evidence) и отдельная БД?

<a id="q-21"></a>**Q-21.** Чарджбэки и диспуты — вне скоупа?

<a id="q-22"></a>**Q-22.** Целевая версия PostgreSQL (предложение — 16 или 17; 18 даёт встроенный `uuidv7()`)?

<a id="q-23"></a>**Q-23.** Инструмент миграций — golang-migrate или Goose? Разрешены ли down-миграции для финансовых таблиц?

<a id="q-24"></a>**Q-24.** Владелец таблицы `holds` — модуль Ledger (предложение) или Payments/Accounts?

<a id="q-25"></a>**Q-25.** Нужны ли партиционирование ledger и архивирование в горизонте проекта, или достаточно индексов и снапшотов?

<a id="q-26"></a>**Q-26.** Требования к порядку событий для потребителей Kafka: строгий порядок по агрегату или достаточно версии в событии?

<a id="q-27"></a>**Q-27.** Библиотеки для тестов: `testcontainers-go` или docker-compose для интеграционных тестов; `rapid` или `testing/quick` для property-based?
