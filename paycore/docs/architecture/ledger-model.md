# Финансовая модель Ledger

Статус: **принято для MVP** (этап 2). Решения — в [decisions.md](decisions.md), нерешённое — в [open-questions.md](open-questions.md).

Связанные документы: [chart-of-accounts.md](chart-of-accounts.md) (план счетов), [money-flows.md](money-flows.md) (проводки по сценариям), [../database/database-schema.md](../database/database-schema.md) (таблицы), [../database/data-integrity.md](../database/data-integrity.md) (неизменяемость), [../database/concurrency.md](../database/concurrency.md) (конкурентность).

## 1. Принципы

1. **Ledger — единственный первоисточник** финансовой истории. Все балансы производны от проводок (ТЗ §2.3).
2. **Двойная запись.** Каждая финансовая операция — журнал (`journal_transactions`) из ≥ 2 проводок (`ledger_entries`). По каждой валюте \(\sum Debit = \sum Credit\).
3. **Неизменяемость (append-only).** Проведённые журналы и проводки не изменяются и не удаляются. Исправление — только новым журналом: сторно (reversal) или корректировкой (adjustment).
4. **Раздельный учёт валют.** У ledger-счёта ровно одна валюта. FX вне скоупа ([D-30](decisions.md#d-30)).
5. **Целые числа.** Суммы — `BIGINT` в минимальных единицах валюты. Никаких `float`, включая DTO и JSON.
6. **Атомарность.** Журнал, проводки, проекции балансов, статус резерва, статус бизнес-объекта, история статусов, outbox-событие и ключ идемпотентности записываются в одной транзакции PostgreSQL (ТЗ §4.7).
7. **Идемпотентность проведения.** Один бизнес-шаг проводится не более одного раза: `UNIQUE (reference_type, reference_id, operation, operation_seq)`.
8. **Единственная точка записи.** В ledger пишет только функция `ledger.post_journal` ([D-03](decisions.md#d-03)). У роли приложения нет прямых прав на запись в ledger-таблицы.
9. **Ledger не знает бизнес-правил.** Он проверяет только бухгалтерские инварианты (баланс, валюта, неотрицательность, статус счёта, допустимость операции). Правила платежей, переводов и комиссий принадлежат своим модулям.
10. **Ledger не знает о симуляции.** Симулятор для ledger — внешний контрагент, представленный счётом 1100 ([D-15](decisions.md#d-15)).

## 2. Термины

| Термин | Таблица | Значение |
|---|---|---|
| Бизнес-счёт | `accounts.accounts` | Счёт, который видит клиент или магазин: «Основной RUB». Номер, валюта, статус, владелец. |
| Ledger-счёт | `ledger.ledger_accounts` | Учётный счёт плана счетов. Бизнес-счёт ↔ **два** ledger-счёта (доступно / резерв). Системные ledger-счета (доход, источник средств) не привязаны к бизнес-счёту. |
| Журнал | `ledger.journal_transactions` | Одна атомарная финансовая операция: набор сбалансированных проводок с общей ссылкой на бизнес-операцию. |
| Проводка | `ledger.ledger_entries` | Строка: ledger-счёт, сторона (DEBIT/CREDIT), сумма > 0, валюта. |
| Резерв (hold) | `ledger.holds` | «Зарезервировано N на счёте X для платежа Y». Создаётся и меняет статус только вместе с журналами `HOLD_*`. |
| Проекция бизнес-счёта | `ledger.account_balances` | `available_amount` / `reserved_amount`. Обновляется в той же транзакции, что и проводки. Это строка блокировки для защиты от двойного списания. |
| Проекция системного счёта | `ledger.system_balance_buckets` | N строк-бакетов на системный ledger-счёт. Баланс = сумма бакетов ([§7.3](#73-проекция-системных-счетов-бакеты)). |
| Операция (operation) | `journal_transactions.operation` | Код типа журнала из закрытого перечня (§6). |

## 3. Представление денег

- Тип в БД — `BIGINT`. В Go — собственные типы `money.Amount` (int64) и `money.Currency`. API пакета `pkg/money` проектируется на этапе реализации.
- Справочник `currencies(code CHAR(3) PK, minor_units SMALLINT, …)`. MVP: RUB и USD, оба с `minor_units = 2` ([D-30](decisions.md#d-30)).
- «100 ₽ = 10 000 копеек» верно для `minor_units = 2`. Преобразование «человеческой» суммы выполняется только на границе (DTO/UI) и только из строки, без float.
- **`MAX_AMOUNT = 10^14`** минорных единиц — технический предел, CHECK на проводках ([D-35](decisions.md#d-35)). \(10^{14} \times 10^4\) bp \(= 10^{18} < 9{,}2 \times 10^{18}\), поэтому умножение на ставку не переполняет `int64`. Бизнес-ограничения задаются лимитами ([D-24](decisions.md#d-24)).
- Арифметика с деньгами — функции с проверкой переполнения, которые возвращают ошибку.
- Округление — **только** в Commission Engine ([§9](#9-комиссии-и-округление)).
- В API сумма передаётся целым числом в минорных единицах вместе с кодом валюты (ТЗ §5: `"amount": 500000`).

## 4. Структура журнала и проводки

**Журнал** (`journal_transactions`):

| Поле | Назначение |
|---|---|
| `id` | UUIDv7 (генерирует Go, передаётся в функцию) |
| `operation` | Код операции (§6) |
| `reference_type`, `reference_id` | Бизнес-объект: `SIM_TOPUP`, `TRANSFER`, `HOLD`, `REFUND`, `PAYOUT`, `ADJUSTMENT` |
| `operation_seq` | По умолчанию 1. Резерв для повторяющихся операций одного объекта |
| `reverses_journal_id` | Ссылка на сторнируемый журнал (только `REVERSAL`) |
| `status` | Всегда `POSTED` ([D-06](decisions.md#d-06)) |
| `description`, `initiated_by` | Описание и инициатор (пользователь, сотрудник или система) |
| `accounting_date` | Учётная дата, UTC ([D-29](decisions.md#d-29)) |
| `posted_at` | Время проведения |

**Проводка** (`ledger_entries`):

| Поле | Назначение |
|---|---|
| `id` | UUIDv7 |
| `journal_transaction_id` | Журнал |
| `ledger_account_id` | Ledger-счёт |
| `entry_type` | `DEBIT` / `CREDIT` |
| `amount` | `> 0` и `<= MAX_AMOUNT` |
| `currency` | Совпадает с валютой ledger-счёта (составной FK) |
| `account_version` | Версия `account_balances` после проводки. Только для счетов клиентов и магазинов ([D-16](decisions.md#d-16)) |
| `balance_after` | Остаток ledger-счёта после проводки в направлении нормального сальдо. Только для счетов клиентов и магазинов |
| `created_at` | Время записи |

Правила:

1. `amount > 0`. Знак задаёт только `entry_type` (ТЗ §4.4 п.1).
2. ≥ 2 проводок; \(\sum DEBIT = \sum CREDIT\) по каждой валюте (ТЗ §4.4 п.2).
3. Не больше одной проводки на ledger-счёт в журнале.
4. Валюта проводки = валюта ledger-счёта (ТЗ §4.4 п.5).
5. Журнал и **все** его проводки создаются одним вызовом `ledger.post_journal` ([data-integrity.md §4](../database/data-integrity.md#4-неизменяемость-ledger)).

## 5. Правила дебета и кредита

Классическая модель «Активы + Расходы = Обязательства + Капитал + Доходы».

| Класс | Код CoA | Нормальное сальдо | Дебет | Кредит | Знаковый баланс |
|---|---|---|---|---|---|
| Активы (ASSET) | 1xxx | Дебетовое | ↑ | ↓ | \(\sum D - \sum C\) |
| Обязательства (LIABILITY) | 2xxx | Кредитовое | ↓ | ↑ | \(\sum C - \sum D\) |
| Капитал (EQUITY) | 3xxx | Кредитовое | ↓ | ↑ | \(\sum C - \sum D\) |
| Доходы (REVENUE) | 4xxx | Кредитовое | ↓ | ↑ | \(\sum C - \sum D\) |
| Расходы (EXPENSE) | 5xxx | Дебетовое | ↑ | ↓ | \(\sum D - \sum C\) |

Применительно к PayCore:

- **Деньги клиента — обязательство PayCore перед клиентом** (LIABILITY). Зачисление клиенту — **кредит**, списание — **дебет**. Это совпадает с примером ТЗ §2.3: перевод 1 000 ₽ — дебет счёта отправителя, кредит счёта получателя.
- Деньги магазина — тоже обязательство.
- Источник виртуальных средств (1100) — актив: «деньги, которые стоят за обязательствами».
- Комиссии — доход (REVENUE). Компенсации клиентам — расход (EXPENSE).

`ledger_accounts.normal_balance` хранится явно и согласован с классом через CHECK.

\[
balance(a) = \begin{cases}
\sum D_a - \sum C_a, & normal(a) = DEBIT \\
\sum C_a - \sum D_a, & normal(a) = CREDIT
\end{cases}
\]

Для счёта с `allow_negative = false` инвариант — \(balance(a) \ge 0\) после **каждого** журнала. Он обеспечивается в момент проведения через CHECK на проекции ([§7](#7-балансы)).

## 7. Балансы

### 7.1. Остатки бизнес-счёта

| Остаток | Формула | Где хранится |
|---|---|---|
| Доступно | `balance(<acc>:AVAILABLE)` | `account_balances.available_amount` |
| Зарезервировано | `balance(<acc>:HOLD)` = \(\sum\) активных резервов | `account_balances.reserved_amount` |
| Всего | доступно + зарезервировано | вычисляется |

Пример ТЗ §2.2 «доступно 85 000, зарезервировано 5 000» означает: Кт-сальдо 2100 = 8 500 000 коп., 2110 = 500 000 коп., всего 9 000 000 коп.

### 7.2. Проекция бизнес-счёта

- Одна строка `account_balances` на бизнес-счёт: `CHECK (available_amount >= 0 AND reserved_amount >= 0)`. Это последний рубеж против овердрафта (овердрафта в MVP нет).
- `version` растёт на 1 при каждом изменении. Новое значение записывается в `ledger_entries.account_version`. `UNIQUE (ledger_account_id, account_version)` делает потерянное обновление невозможным.
- Строку блокирует `ledger.lock_account_balances` (уровень L5, [concurrency.md §3](../database/concurrency.md#3-единый-порядок-захвата-блокировок)). Изменяет её только `ledger.post_journal`.

### 7.3. Проекция системных счетов (бакеты)

Решение [D-02](decisions.md#d-02) (пересмотрено на этапе 2). Разбор по каждому системному счёту — [chart-of-accounts.md §3](chart-of-accounts.md#3-системные-счета-остаток-контроль-проекция).

- `system_balance_buckets(ledger_account_id, bucket_no, balance, updated_at)`, где `bucket_no ∈ [0, bucket_count)`. Для `allow_negative = false` действует `CHECK (balance >= 0)`.
- **Увеличение** остатка (проводка в сторону нормального сальдо): `UPDATE … SET balance = balance + amount WHERE ledger_account_id = $a AND bucket_no = hash(journal_id) % bucket_count`. Блокируется одна строка, и только до конца транзакции.
- **Уменьшение**: `SELECT … WHERE ledger_account_id = $a ORDER BY bucket_no FOR UPDATE` (все бакеты). Если `SUM(balance) < amount` — ошибка. Иначе сумма списывается из бакетов по порядку, пока не будет покрыта.
- Каждый бакет ≥ 0, поэтому сумма ≥ 0 в момент коммита. Отрицательный остаток невозможен, сверка для этого не нужна.
- Текущий баланс — `SELECT SUM(balance)` по бакетам (≤ 16 строк).
- Если счёт в одном журнале уменьшается, а другой увеличивается, функция обрабатывает счета в порядке `(ledger_account_id, bucket_no)` (уровень L6).

### 7.4. Восстановление баланса по истории (ТЗ §2.3)

Любая проекция воспроизводима из `ledger_entries` (иллюстративно):

```sql
SELECT e.ledger_account_id,
       SUM(CASE WHEN e.entry_type = a.normal_balance THEN e.amount ELSE -e.amount END) AS balance
FROM ledger.ledger_entries e
JOIN ledger.ledger_accounts a ON a.id = e.ledger_account_id
GROUP BY e.ledger_account_id;
```

Для бизнес-счёта результат сравнивается с `account_balances` (AVAILABLE → `available_amount`, HOLD → `reserved_amount`), для системного — с `SUM` бакетов (инвариант I-03). Остаток на дату берётся из последнего `balance_after` до даты (бизнес-счета) или тем же запросом с фильтром по `posted_at` (системные).

## 8. Резервирование (hold)

Решение [D-01](decisions.md#d-01): **резерв — это проводка** между двумя субсчетами одного клиента.

```
HOLD_PLACE:    Дт A:2100 (доступно)   Кт A:2110 (резерв)                             сумма резерва
HOLD_RELEASE:  Дт A:2110              Кт A:2100
HOLD_CAPTURE:  Дт A:2110              Кт MA:2200 (amount − fee) + Кт 4200:<cur> (fee)
```

- При резервировании общее обязательство перед клиентом (2100 + 2110) не меняется, меняется только доступность.
- Таблица `holds` (статусы `ACTIVE → CAPTURED | RELEASED | EXPIRED`) изменяется **только** функцией `ledger.post_journal` в том же вызове, что и журнал `HOLD_*`. Поэтому I-05 (`reserved_amount` = \(\sum\) ACTIVE-резервов) гарантируется конструктивно.
- MVP: один резерв на платёж и один capture на полную сумму ([D-36](decisions.md#d-36)).

## 9. Комиссии и округление

- Тарифы `commission_tariffs` версионируются, периоды действия не пересекаются (EXCLUDE) — ТЗ §2.7.
- Параметры тарифа: `rate_bp` (1 bp = 0,01 %), `fixed_amount`, `min_amount`, `max_amount`, `rounding_mode`, `currency`, `operation_type`, `merchant_id` (персональный тариф).
- Формула:
  1. `raw = amount × rate_bp`;
  2. `fee = round(raw / 10 000, rounding_mode)`;
  3. `fee += fixed_amount`;
  4. `fee = clamp(fee, min_amount, max_amount)`.

  Для `HALF_UP` и положительных чисел шаг 2 — это `(raw + 5 000) / 10 000` целочисленно.
- Примеры:
  - перевод 1 000 ₽ = 100 000 коп. × 50 bp → 500 коп., меньше min → **1 000 коп. (10 ₽)**;
  - платёж 5 000 ₽ = 500 000 × 150 bp → **7 500 коп. (75 ₽)**;
  - платёж 1 000 ₽ = 100 000 × 150 bp → **1 500 коп. (15 ₽)**;
  - 333 коп. × 150 bp = 49 950 → 4,995 → **5** (до min).
- **Кто и когда** ([D-08](decisions.md#d-08), [D-27](decisions.md#d-27)):
  - перевод — отправитель сверх суммы, расчёт в транзакции перевода;
  - платёж — магазин, удерживается при capture, расчёт в транзакции capture по тарифу на момент capture.
- Результат фиксируется в бизнес-объекте (`fee_amount`, `fee_tariff_id`) в той же транзакции, где строится журнал.
- Граница: если по тарифу `fee >= amount`, платёж не создаётся (`AMOUNT_TOO_SMALL`). При capture действует `fee = min(fee, amount)` и CHECK `fee_amount <= amount`.
- Возврат не возвращает комиссию ([D-09](decisions.md#d-09)).

## 10. Неизменяемость и исправления

- Права, функция-шлюз и триггеры — [data-integrity.md §4](../database/data-integrity.md#4-неизменяемость-ledger).
- **Сторно (REVERSAL)** — новый журнал с зеркальными проводками и `reverses_journal_id`. Повторное сторно запрещено (`UNIQUE`). Сторно сторно запрещено (CHECK в функции): повторное исправление делается корректировкой.
- **Корректировка (ADJUSTMENT)** — сбалансированный журнал по заявке `manual_adjustments`: OPERATOR создаёт, ADMIN утверждает, `approved_by <> created_by` ([D-31](decisions.md#d-31)).
- Сторно и корректировки проходят через те же проверки неотрицательности, что и обычные операции. Если средств на счёте уже нет, проведение отклоняется, и оператор выбирает другое решение.
- Бизнес-операции (возврат, void) — **не** сторно, а самостоятельные операции.

## 11. Контракт проведения

### 11.1. Go: `Ledger.Post` (концептуально)

1. Принимает `operation`, `reference_type/id`, проводки `(ledger_account, side, amount)`, опционально действие над резервом (`PLACE` / `CAPTURE` / `RELEASE` / `EXPIRE` + `hold_id`, сумма, срок), описание, инициатора.
2. Валидирует в домене те же правила, что и функция. Это нужно для понятных ошибок и unit-тестов без БД.
3. Вызывает `ledger.post_journal` внутри транзакции use case (Unit of Work). Транзакцией владеет вызывающий use case.
4. Отображает SQLSTATE функции в доменные ошибки (§11.3).

### 11.2. SQL: `ledger.post_journal(...)` — `SECURITY DEFINER`

Порядок действий внутри функции:

1. Проверить, что журнала с таким `(reference_type, reference_id, operation, operation_seq)` нет. Если есть — сравнить проводки:
   - совпадают → вернуть существующий журнал с флагом `already_posted` (идемпотентный ответ);
   - отличаются → `PC409`.
2. Валидация: ≥ 2 проводок; `0 < amount ≤ MAX`; \(\sum D = \sum C\) по каждой валюте; нет дублей счёта; счета существуют, `ACTIVE`, валюта совпадает; операция допустима; для `REVERSAL` — исходный журнал существует и сам не является сторно.
3. Отсортировать затронутые проекции: сначала бизнес-счета по `account_id` (L5; строки уже заблокированы вызывающим через `lock_account_balances`), затем системные бакеты по `(ledger_account_id, bucket_no)` (L6). Резерв (`holds`) меняется последним (L7) — [concurrency.md §3](../database/concurrency.md#3-единый-порядок-захвата-блокировок).
4. Обновить `account_balances` (`version + 1`, вернуть новые версию и остатки). Обновить бакеты (§7.3). Нарушение CHECK → `PC402`.
5. Вставить журнал (`POSTED`) и все проводки с `account_version` / `balance_after`.
6. Выполнить действие над `holds` (вставка `ACTIVE` или переход из `ACTIVE`; переход из другого статуса → `PC409`).
7. Вернуть id журнала и проводки с остатками.

Отложенный constraint trigger на `COMMIT` повторно проверяет баланс журнала (страховка, [data-integrity.md §4.4](../database/data-integrity.md#44-вторая-линия-триггеры)).

### 11.3. Коды ошибок функций

| SQLSTATE | Доменная ошибка |
|---|---|
| `PC400` | `INVALID_JOURNAL` (несбалансирован, < 2 проводок, сумма вне диапазона, валюта) — баг вызывающего |
| `PC402` | `INSUFFICIENT_FUNDS` (проекция бизнес-счёта) / `SYSTEM_ACCOUNT_INSUFFICIENT` (бакеты — баг, алерт) |
| `PC403` | `ACCOUNT_NOT_ACTIVE` |
| `PC409` | `CONFLICT` (повтор с другим содержимым, неверный переход резерва) |

## 12. Финансовые инварианты

Проверяются тестами ([financial-invariants-testing.md](financial-invariants-testing.md)) и задачей контроля в production. Колонка «Гарантия» показывает, где инвариант обеспечен **в момент записи**. Задача контроля дополнительно ловит ошибки в самих механизмах.

| ID | Инвариант | Гарантия в момент записи |
|---|---|---|
| I-01 | По каждому журналу и валюте \(\sum D = \sum C\), ≥ 2 проводок | `post_journal` + отложенный триггер |
| I-02 | Глобально по каждой валюте \(\sum D = \sum C\) | следствие I-01 |
| I-03 | Проекции (`account_balances`, `SUM` бакетов) = пересчёт по проводкам | обновляются в том же вызове `post_journal`; прямой записи нет (права) |
| I-04 | Для `allow_negative = false` баланс ≥ 0 в каждой точке истории | CHECK на `account_balances` и бакетах |
| I-05 | `reserved_amount` = \(\sum\) ACTIVE-резервов = balance(HOLD) | `holds` меняются только в `post_journal` |
| I-06 | `refunded_amount` ≤ `captured_amount` и = \(\sum\) успешных возвратов | CHECK + блокировка платежа (L2) |
| I-07 | Проведённые записи не изменялись | права + триггеры |
| I-08 | Каждый бизнес-шаг проведён ≤ 1 раза | `UNIQUE` журнала |
| I-09 | Цепочка `balance_after` / `account_version` согласована | вычисляется в `post_journal` под блокировкой; `UNIQUE` версии |
| I-10 | Статус бизнес-объекта согласован с журналами | одна транзакция use case; контроль — задача проверки |
| I-11 | Валюта проводки = валюта счёта = валюта объекта | составные FK |
| I-12 | `fee_amount` = кредиту дохода и воспроизводится по `fee_tariff_id` | одна транзакция; контроль — задача проверки |
