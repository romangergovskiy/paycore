# План счетов (Chart of Accounts)

Статус: **принято для MVP** (этап 2). Правила дебета и кредита — [ledger-model.md §5](ledger-model.md#5-правила-дебета-и-кредита). Использование счетов в сценариях — [money-flows.md](money-flows.md). Решения — [decisions.md](decisions.md).

## 1. Принципы

- План счетов задаёт **типы** ledger-счетов (`account_type` = код CoA, справочник `ledger.chart_of_accounts`). Конкретный ledger-счёт — это тип + владелец + валюта.
- **Счета клиентов и магазинов** (2100/2110, 2200/2210) создаются функцией `ledger.open_ledger_accounts` при открытии бизнес-счёта: пара «доступно + резерв» в валюте счёта.
- **Системные счета** создаются сидом на каждую активную валюту: `<код>:<валюта>`, например `4200:RUB`. В MVP валюта одна — RUB ([D-30](decisions.md#d-30)), поэтому системных счетов четыре: `1100:RUB`, `4100:RUB`, `4200:RUB`, `5900:RUB`. Включение новой валюты — тот же сид для неё. Владелец — `SYSTEM`. Код для приложения — `system_code`.
- Коды условные, это не план счетов ЦБ РФ. Модель демонстрационная, деньги виртуальные ([D-20](decisions.md#d-20)).
- **У каждого ledger-счёта есть синхронная проекция** ([D-02](decisions.md#d-02)): у счетов клиентов и магазинов — строка `account_balances`, у системных — бакеты `system_balance_buckets`.

## 3. Системные счета: остаток, контроль, проекция

Ответ на вопрос этапа 2 §3.1 — по каждому системному счёту MVP. Механизм бакетов описан в [ledger-model.md §7.3](ledger-model.md#73-проекция-системных-счетов-бакеты), блокировки — в [concurrency.md §8](../database/concurrency.md#8-горячие-точки-и-масштабирование).

| Счёт | Отрицательный остаток | Что увеличивает (частота) | Что уменьшает (частота) | Контроль допустимого остатка | Текущий баланс | Проекция | Как избежать горячей строки |
|---|---|---|---|---|---|---|---|
| **1100** Источник виртуальных средств | **Запрещён.** Остаток = обязательства + доход − компенсации (§5) | `SIM_TOPUP` — Дт (часто) | `PAYOUT` — Кт (редко), сторно пополнения | `CHECK (balance >= 0)` на **каждом** бакете. Уменьшение блокирует все бакеты, проверяет сумму и распределяет списание. Нехватка → `PC402 SYSTEM_ACCOUNT_INSUFFICIENT`: выплата сохраняется как `FAILED (PAYOUT_SOURCE_INSUFFICIENT)`, алерт (см. ниже) | `SUM(balance)` по бакетам | **Да**, синхронная, 16 бакетов | Пополнение пишет в один бакет `hash(journal_id) % 16`. Блокировка всех бакетов — только при редкой выплате |
| **4100** Доход переводы | **Запрещён** | Комиссия перевода — Кт (очень часто) | Только `ADJUSTMENT` / `REVERSAL` (единично) | Как у 1100 | `SUM` по бакетам | **Да**, 16 бакетов | Как у 1100. Увеличение коммутативно, поэтому строки «Доход» не являются точкой сериализации |
| **4200** Доход платежи | **Запрещён** | Комиссия при capture — Кт (очень часто) | Только `ADJUSTMENT` / `REVERSAL` | Как у 1100 | `SUM` по бакетам | **Да**, 16 бакетов | Как у 4100 |
| **5900** Потери и компенсации | **Запрещён** | `ADJUSTMENT` — Дт (единично) | `REVERSAL` корректировки | Как у 1100 | `SUM` | **Да**, 1 бакет | Не нужно: операции единичные |

Почему бакеты, а не одна строка. Каждая комиссия кредитует 4100 или 4200. При одной строке все платежи и переводы платформы выстроились бы в очередь на её блокировке (риск R-01). Бакеты снимают это для частой операции (увеличение), а дорогая полная блокировка остаётся только у редкой (уменьшение).

Почему не «без проекции». Тогда запрещённый отрицательный остаток системного счёта обнаружился бы только сверкой. Этап 2 это запрещает.

Когда 1100 может не хватить на выплату. Из §5 в MVP: \(1100 = \sum 2xxx + (4100 + 4200) - 5900\). Выплата не больше доступного остатка магазина, а он входит в \(\sum 2xxx\). Значит, после выплаты \(1100 \ge (4100 + 4200) - 5900\). Пока компенсации (5900) не превышают комиссионный доход, выплата никогда не упрётся в CHECK бакетов. Если превысят (компенсации создают обязательства без поступления в 1100), последние выплаты будут отклоняться, а не уводить 1100 в минус. Бакеты блокирует только функция, поэтому use case выплаты вызывает `post_journal` внутри `SAVEPOINT`: при `PC402 SYSTEM_ACCOUNT_INSUFFICIENT` он откатывается к точке сохранения и сохраняет выплату как `FAILED` в той же транзакции ([concurrency.md §5.6](../database/concurrency.md#56-тестовое-пополнение-и-выплата)). Порог «компенсации ≤ доход» показывается ADMIN при утверждении корректировки ([D-31](decisions.md#d-31)).

Почему у бакетов нет `account_version` / `balance_after`. Порядок бакетов не линейный. Цепочку остатков системного счёта восстанавливает запрос по `ledger_entries` (окно по `posted_at`, `id`). Согласованность с проводками проверяет I-03.

Счета «после MVP» (1200, 1300, 2300, 2900, 4900, 5100) при включении получают ту же схему. Для счетов с `allow_negative = true` (2900) CHECK на бакетах не ставится.

## 4. Отображение на таблицы

| Сущность | `owner_type` | `account_id` | `account_type` | `kind` | Проекция |
|---|---|---|---|---|---|
| Счёт клиента «Основной RUB» | CUSTOMER | id бизнес-счёта | 2100 и 2110 | AVAILABLE / HOLD | `account_balances` (одна строка на оба ledger-счёта) |
| Счёт магазина (RUB) | MERCHANT | id бизнес-счёта магазина | 2200 и 2210 | AVAILABLE / HOLD | `account_balances` |
| Доход от платежей, RUB | SYSTEM | NULL | 4200 | — | `system_balance_buckets` (16 строк) |

- Уникальность: `UNIQUE (account_id, kind)` для пользовательских ledger-счетов, `UNIQUE (system_code, currency)` для системных.
- Магазин получает один бизнес-счёт на каждую валюту приёма платежей; в MVP — один счёт в RUB. Несколько магазинов (`stores`) одного мерчанта используют общий счёт.

## 5. Проверка «баланса баланса»

По каждой валюте в любой момент (в MVP — только RUB):

\[
\sum_{1xxx} + \sum_{5xxx} = \sum_{2xxx} + \sum_{3xxx} + \sum_{4xxx}
\]

Это эквивалентно I-02 (\(\sum D = \sum C\) по всем проводкам). В MVP это сводится к простому равенству: **1100 + 5900 = все счета клиентов и магазинов + 4100 + 4200**. Пробный баланс (trial balance) — отчёт Admin Dashboard.
