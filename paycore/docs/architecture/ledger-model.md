# Финансовая модель Ledger

Статус: **проект, требует согласования**. Спорные места помечены ссылками на [open-questions.md](open-questions.md).

Связанные документы: [chart-of-accounts.md](chart-of-accounts.md) (план счетов), [money-flows.md](money-flows.md) (проводки по сценариям), [../database/database-schema.md](../database/database-schema.md) (таблицы), [../database/concurrency.md](../database/concurrency.md) (конкурентность).

## 1. Принципы

1. **Ledger — единственный первоисточник** финансовой истории. Все балансы являются производными от проводок (ТЗ §2.3).
2. **Двойная запись.** Каждая финансовая операция — это журнал (`journal_transactions`) из двух и более проводок (`ledger_entries`). В каждой валюте \(\sum Debit = \sum Credit\).
3. **Неизменяемость (append-only).** Проведённые журналы и проводки никогда не меняются и не удаляются. Исправление делается только новым журналом: сторно (reversal) или корректировкой (adjustment).
4. **Раздельный учёт валют.** Ledger-счёт имеет ровно одну валюту. Журнал может содержать несколько валют только в FX-сценарии, который вне скоупа MVP.
5. **Целые числа.** Суммы хранятся как `BIGINT` в минимальных единицах валюты. Значения с плавающей точкой (`float`) не используются нигде, включая DTO и JSON.
6. **Атомарность.** Журнал, проводки, обновление проекции баланса, смена статуса бизнес-объекта и outbox-событие записываются в одной транзакции PostgreSQL (ТЗ §4.7).
7. **Идемпотентность проведения.** Один бизнес-шаг (например, «capture платежа X») может быть проведён не более одного раза. Это гарантирует уникальный ключ `(reference_type, reference_id, operation)`.
8. **Ledger не знает бизнес-правил.** Ledger проверяет только бухгалтерские инварианты: баланс, валюты, запрет отрицательного остатка, статус счёта. Правила платежей, переводов и комиссий принадлежат соответствующим модулям.

## 2. Термины

| Термин | Таблица | Значение |
|---|---|---|
| Бизнес-счёт | `accounts` | Счёт, который видит клиент или мерчант: «Основной RUB». Имеет номер, валюту, статус и владельца. |
| Ledger-счёт | `ledger_accounts` | Учётный счёт из плана счетов. Бизнес-счёт отображается на **два** ledger-счёта: «доступно» и «резерв». Системные ledger-счета (доходы, клиринг) не привязаны к бизнес-счёту. |
| Журнал | `journal_transactions` | Одна атомарная финансовая операция: набор сбалансированных проводок с общей ссылкой на бизнес-операцию. |
| Проводка | `ledger_entries` | Одна строка: ledger-счёт, сторона (DEBIT/CREDIT), сумма > 0, валюта. |
| Резерв (hold) | `holds` | Бизнес-объект «зарезервировано N на счёте X для Y». Его денежная сторона — журналы `HOLD_PLACE` / `HOLD_CAPTURE` / `HOLD_RELEASE`. |
| Проекция баланса | `account_balances` | Кэш `available_amount` / `reserved_amount` для бизнес-счёта. Обновляется синхронно с проводками и служит строкой блокировки для защиты от двойного списания. |
| Операция (operation) | `journal_transactions.operation` | Код типа журнала из закрытого перечня (§6). |

## 3. Представление денег

- Тип в БД: `BIGINT`. Тип в Go: собственный тип `money.Amount` (int64) и `money.Currency`. Конкретный API пакета `pkg/money` проектируется на следующем этапе.
- Справочник `currencies(code CHAR(3) PK, minor_units SMALLINT, ...)`. Код — ISO 4217. `minor_units` — число знаков после запятой: RUB = 2, USD = 2, JPY = 0. Набор валют — [Q-08](open-questions.md#q-08).
- «100 ₽ = 10 000 копеек» верно только для `minor_units = 2`. Преобразование «человеческой» суммы в минорные единицы выполняется только на границе (DTO/UI) и только из строки или целого, без float.
- **Максимальная сумма** одной операции — `MAX_AMOUNT`. Предлагается \(10^{15}\) минорных единиц (\(10^{13}\) ₽) или меньше. Значение должно гарантировать, что `amount × rate_bp` помещается в `int64`: \(10^{15} \times 10^4 = 10^{19}\) уже переполняет int64 (\(9{,}2 \times 10^{18}\)). Поэтому нужно либо снизить лимит до \(10^{14}\), либо считать через 128-битное умножение (`math/bits.Mul64`) или `math/big`. Рекомендация: лимит \(10^{14}\) **и** проверка переполнения в арифметике (checked arithmetic). Вопрос — [Q-11](open-questions.md#q-11).
- Все арифметические операции над деньгами (сложение, вычитание, процент) выполняются через функции с проверкой переполнения и возвращают ошибку, а не значение с переполнением.
- Округление выполняется **в одном месте** — в Commission Engine — по явно заданному правилу ([§9](#9-комиссии-и-округление), [D-17](open-questions.md#d-17)).
- Сумма в API передаётся целым числом в минорных единицах вместе с кодом валюты, как в примере ТЗ (`"amount": 500000`).

## 4. Структура журнала и проводки

**Журнал** (`journal_transactions`):

| Поле | Назначение |
|---|---|
| `id` | UUIDv7 |
| `operation` | Код операции (§6) |
| `reference_type`, `reference_id` | Бизнес-объект: `TRANSFER`, `PAYMENT`, `REFUND`, `HOLD`, `TOPUP`, `PAYOUT`, `ADJUSTMENT` |
| `reverses_journal_id` | Ссылка на журнал, который сторнируется (только для `REVERSAL`) |
| `status` | Всегда `POSTED` ([D-06](open-questions.md#d-06)) |
| `description` | Человекочитаемое описание |
| `posted_at` | Время проведения |
| `accounting_date` | Учётная дата ([Q-17](open-questions.md#q-17)) |
| `created_by` | Инициатор: пользователь, система или сотрудник (для аудита) |

Ключ идемпотентности проведения: `UNIQUE (reference_type, reference_id, operation)`. Для операций, которые законно повторяются по одному объекту, есть два варианта: несколько частичных возвратов делаются отдельными объектами `refunds` с собственными id, а несколько подтверждений одного платежа ([Q-06](open-questions.md#q-06)) различаются полем `operation_seq`.

**Проводка** (`ledger_entries`):

| Поле | Назначение |
|---|---|
| `id` | UUIDv7 |
| `journal_transaction_id` | Журнал |
| `ledger_account_id` | Ledger-счёт |
| `entry_type` | `DEBIT` / `CREDIT` |
| `amount` | `> 0` и `<= MAX_AMOUNT` |
| `currency` | Обязана совпадать с валютой ledger-счёта (составной FK) |
| `account_version` | Версия проекции счёта после этой проводки. Только для счетов с проекцией, иначе NULL ([D-16](open-questions.md#d-16)) |
| `balance_after` | Остаток ledger-счёта после проводки, в направлении нормального сальдо. Только для счетов с проекцией |
| `created_at` | Время записи |

Правила:

1. `amount > 0`. Знак задаётся только `entry_type`, отрицательных сумм нет (ТЗ §4.4 п.1).
2. Журнал содержит не меньше двух проводок, и в каждой валюте \(\sum DEBIT = \sum CREDIT\) (ТЗ §4.4 п.2).
3. В одном журнале не больше одной проводки на один ledger-счёт: `UNIQUE (journal_transaction_id, ledger_account_id)`. Это упрощает `balance_after` и исключает «шумные» проводки «дебет и кредит одного счёта».
4. Валюта проводки равна валюте ledger-счёта (ТЗ §4.4 п.5).
5. Проводки добавляются только в той же транзакции, в которой создан журнал. После коммита журнал «закрыт» ([data-integrity.md §4](../database/data-integrity.md#4-триггеры-и-защита-неизменяемости)).

## 5. Правила дебета и кредита

Классическая модель: «Активы + Расходы = Обязательства + Капитал + Доходы».

| Класс | Код CoA | Нормальное сальдо | Дебет | Кредит | Знаковый баланс |
|---|---|---|---|---|---|
| Активы (ASSET) | 1xxx | Дебетовое | ↑ увеличивает | ↓ уменьшает | \(\sum D - \sum C\) |
| Обязательства (LIABILITY) | 2xxx | Кредитовое | ↓ уменьшает | ↑ увеличивает | \(\sum C - \sum D\) |
| Капитал (EQUITY) | 3xxx | Кредитовое | ↓ | ↑ | \(\sum C - \sum D\) |
| Доходы (REVENUE) | 4xxx | Кредитовое | ↓ | ↑ | \(\sum C - \sum D\) |
| Расходы (EXPENSE) | 5xxx | Дебетовое | ↑ | ↓ | \(\sum D - \sum C\) |

Применительно к PayCore (с точки зрения бухгалтерии платёжной организации):

- **Деньги клиента на счёте — это обязательство PayCore перед клиентом** (LIABILITY). Зачисление клиенту — **кредит** его счёта, списание — **дебет**. Это совпадает с примером ТЗ §2.3: перевод 1 000 ₽ — дебет счёта отправителя, кредит счёта получателя.
- Деньги мерчанта — также обязательство (LIABILITY).
- Деньги PayCore на (симулированном) банковском счёте и требования к провайдеру — активы (ASSET).
- Комиссии — доход (REVENUE), кредитовое сальдо.
- Потери, списания и комиссии провайдера — расходы (EXPENSE).

`ledger_accounts.normal_balance` хранится явно (`DEBIT`/`CREDIT`) и выводится из класса, что проверяется CHECK. Знаковый баланс счёта считается по формуле:

\[
balance(a) = \begin{cases}
\sum D_a - \sum C_a, & normal(a) = DEBIT \\
\sum C_a - \sum D_a, & normal(a) = CREDIT
\end{cases}
\]

Для счёта с `allow_negative = false` инвариант — \(balance(a) \ge 0\) после каждого журнала.

## 6. Перечень операций (operation)

Закрытый перечень. Добавление нового кода выполняется через миграцию и ревью.

| Код | reference_type | Описание | Сценарий |
|---|---|---|---|
| `TOPUP` | TOPUP | Пополнение счёта клиента из внешнего (симулированного) банка | [§3](money-flows.md#3-пополнение-счёта-предпосылка) |
| `TRANSFER` | TRANSFER | Прямое проведение перевода (с комиссией) | [§4](money-flows.md#4-переводы) |
| `HOLD_PLACE` | HOLD | Резервирование: доступно → резерв | [§4.3](money-flows.md#43-перевод-с-ручной-проверкой-review), [§5](money-flows.md#5-платёж-создание--авторизация--подтверждение) |
| `HOLD_CAPTURE` | HOLD | Списание из резерва с зачислением получателю (и комиссией) | там же |
| `HOLD_RELEASE` | HOLD | Освобождение резерва: резерв → доступно | [§6](money-flows.md#6-отмена-авторизации-void), [§9](money-flows.md#9-истечение-авторизации) |
| `REFUND` | REFUND | Возврат по платежу (полный или частичный) | [§10](money-flows.md#10-возвраты) |
| `PAYOUT_INIT` / `PAYOUT_SETTLE` / `PAYOUT_FAIL` | PAYOUT | Выплата мерчанту | [§12](money-flows.md#12-выплата-мерчанту-payout) |
| `REVERSAL` | исходный тип | Полное сторно журнала (зеркальные проводки) | [§13](money-flows.md#13-исправление-ошибок-сторно-и-корректировка) |
| `ADJUSTMENT` | ADJUSTMENT | Ручная корректировка по процедуре maker-checker | там же |

`HOLD_CAPTURE` использует `reference_type = HOLD`, а связь с платежом или переводом лежит в `holds.reference_*`. Альтернатива — `reference_type = PAYMENT, operation = CAPTURE`. Выбирается одна схема для всех случаев; рекомендация — привязка к `HOLD`, потому что жизненный цикл резерва одинаков для платежей и переводов.

## 7. Балансы

### 7.1. Виды остатков бизнес-счёта

| Остаток | Формула | Где хранится |
|---|---|---|
| Доступно (available) | `balance(ledger_account <acc>:AVAILABLE)` | `account_balances.available_amount` |
| Зарезервировано (reserved) | `balance(ledger_account <acc>:HOLD)` = \(\sum\) активных резервов | `account_balances.reserved_amount` |
| Всего (ledger / total) | available + reserved | вычисляется |

Пример из ТЗ §2.2: «Основной RUB, доступно 85 000, зарезервировано 5 000». Значит, на счёте 2100 (AVAILABLE) кредитовое сальдо 8 500 000 коп., на счёте 2110 (HOLD) — 500 000 коп., всего — 9 000 000 коп.

### 7.2. Проекция

- `account_balances` существует **только для бизнес-счетов** (клиент и мерчант). Это строка, которую блокируют (`SELECT … FOR UPDATE`) при каждом списании ([concurrency.md](../database/concurrency.md)).
- `CHECK (available_amount >= 0 AND reserved_amount >= 0)` — последняя линия защиты от овердрафта. Если в будущем потребуется овердрафт, CHECK заменяется на `available_amount >= -overdraft_limit` ([Q-18](open-questions.md#q-18)).
- `version` увеличивается при каждом изменении. Новое значение записывается в `ledger_entries.account_version` всех проводок журнала по этому счёту. `UNIQUE (ledger_account_id, account_version)` делает невозможным «потерянное обновление»: две параллельные транзакции не могут записать одну и ту же версию.
- **Системные ledger-счета не имеют синхронной проекции** ([D-02](open-questions.md#d-02)). Их баланс вычисляется агрегатом по `ledger_entries` или по периодическим снапшотам `ledger_balance_snapshots`. Так снимается горячая точка (R-01). Для системных счетов с `allow_negative = false` (их почти нет) проверка выполняется задачей сверки, а не в момент проведения.

### 7.3. Восстановление баланса по истории (ТЗ §2.3)

Проекция бизнес-счёта всегда воспроизводима запросом, иллюстративно:

```sql
SELECT la.account_id,
       SUM(CASE WHEN la.kind = 'AVAILABLE' THEN signed_amount END) AS available,
       SUM(CASE WHEN la.kind = 'HOLD'      THEN signed_amount END) AS reserved
FROM (
  SELECT e.ledger_account_id,
         CASE WHEN e.entry_type = a.normal_balance THEN e.amount ELSE -e.amount END AS signed_amount
  FROM ledger.ledger_entries e
  JOIN ledger.ledger_accounts a ON a.id = e.ledger_account_id
) x
JOIN ledger.ledger_accounts la ON la.id = x.ledger_account_id
GROUP BY la.account_id;
```

Остаток на дату — тот же запрос с фильтром по `posted_at` / `accounting_date`, либо последний `balance_after` до даты (быстрее, используется для выписки).

## 8. Резервирование (hold)

Решение ([D-01](open-questions.md#d-01), вариант A): **резерв — это проводка в ledger** между двумя субсчетами одного клиента.

```
HOLD_PLACE:    Дт 2100 <клиент>:AVAILABLE   Кт 2110 <клиент>:HOLD     (сумма резерва)
HOLD_RELEASE:  Дт 2110 <клиент>:HOLD        Кт 2100 <клиент>:AVAILABLE
HOLD_CAPTURE:  Дт 2110 <клиент>:HOLD        Кт <получатель> (+ Кт <доход от комиссии>)
```

Свойства:

- Общее обязательство перед клиентом (2100 + 2110) при резервировании не меняется. Меняется только доступность средств.
- Остаток `reserved_amount` полностью восстанавливается из ledger.
- Бизнес-объект `holds` хранит статус (`ACTIVE → CAPTURED | RELEASED | EXPIRED`), сумму, срок действия и ссылку на платёж или перевод.
- Инвариант [I-05](#12-финансовые-инварианты): `reserved_amount` счёта = \(\sum\) `holds.amount` в статусе `ACTIVE` = `balance(<acc>:HOLD)`.
- MVP: одно подтверждение на полную сумму. Частичное подтверждение ([Q-06](open-questions.md#q-06)) реализуется как `HOLD_CAPTURE` на часть суммы плюс `HOLD_RELEASE` остатка в **одном** журнале или в двух журналах в одной транзакции.

## 9. Комиссии и округление

- Тариф: `commission_tariffs` с версиями и периодами действия (`valid_from`, `valid_to`), без пересечения периодов (EXCLUDE-ограничение) — ТЗ §2.7.
- Параметры тарифа: `rate_bp` (ставка в базисных пунктах, 1 bp = 0,01 %; 0,5 % = 50 bp, 1,5 % = 150 bp), `fixed_amount`, `min_amount`, `max_amount`, `rounding_mode`, `currency`.
- Формула (целочисленная):
  1. `raw = amount × rate_bp` (с проверкой переполнения);
  2. `fee = round(raw / 10 000, rounding_mode)`;
  3. `fee = fee + fixed_amount`;
  4. `fee = clamp(fee, min_amount, max_amount)`.
- Для `HALF_UP` и положительных чисел: `fee = (raw + 5 000) / 10 000` (целочисленное деление).
- Пример: перевод 1 000 ₽ = 100 000 коп., ставка 50 bp: `raw = 5 000 000`, `fee = 500` коп. (5 ₽). Это меньше min 1 000 коп., поэтому `fee = 1 000` коп. (10 ₽).
- Пример: платёж 5 000 ₽ = 500 000 коп., 150 bp: `fee = 7 500` коп. (75 ₽), в пределах [1 000; 50 000].
- Пример округления: 333 коп. × 150 bp = 49 950 → 4,995 → `HALF_UP` = 5 коп. (до применения min).
- Результат расчёта фиксируется в бизнес-объекте (`fee_amount`, `fee_tariff_id`) **до** проведения. Ledger получает уже готовые суммы.
- Граничный случай: min-комиссия больше суммы платежа (платёж 5 ₽ при min 10 ₽). Мерчант получил бы отрицательную сумму ([Q-09](open-questions.md#q-09)). Предложение: `fee = min(fee, amount)` для платежей, либо минимальная сумма платежа.

## 10. Неизменяемость и исправления

- `UPDATE`, `DELETE` и `TRUNCATE` на `journal_transactions` и `ledger_entries` запрещены дважды: правами роли БД и триггером ([data-integrity.md](../database/data-integrity.md#4-триггеры-и-защита-неизменяемости)).
- **Сторно (REVERSAL)** — новый журнал с зеркальными проводками (DEBIT ↔ CREDIT) и `reverses_journal_id`. Повторное сторно одного журнала запрещено (`UNIQUE` по `reverses_journal_id`). Сторно сторно — открытый вопрос, рекомендуется запретить и делать корректировку.
- **Корректировка (ADJUSTMENT)** — произвольный сбалансированный журнал по заявке `manual_adjustments`, которую создаёт один сотрудник (OPERATOR) и утверждает другой (ADMIN или второй OPERATOR), `approved_by <> created_by`. Так выполняется требование ТЗ §2.1 «ADMIN не перемещает деньги бесконтрольно» ([Q-15](open-questions.md#q-15)).
- Бизнес-операции (возврат, void) — это не сторно, а самостоятельные операции со своими кодами. Сторно применяется только для исправления технических ошибок.

## 11. Контракт сервиса проведения (концептуально)

Не код, а описание обязанностей `Ledger.Post` — единственной точки записи в ledger:

1. Вход: `operation`, `reference_type/id`, список проводок `(ledger_account, side, amount)`, описание, инициатор. Выполняется внутри внешней транзакции, переданной вызывающим use case (Unit of Work).
2. Проверки в Go до записи: не меньше 2 проводок; все суммы > 0 и ≤ MAX; баланс по каждой валюте; валюта каждой проводки = валюте счёта; счета существуют и активны; нет дублей ledger-счёта в журнале; код операции допустим.
3. Блокировка строк `account_balances` затронутых бизнес-счетов **в порядке возрастания `account_id`** (если вызывающий ещё не заблокировал их).
4. Обновление проекции (`available/reserved ± amount`, `version + 1`). Нарушение `CHECK >= 0` даёт доменную ошибку `INSUFFICIENT_FUNDS`.
5. Вставка журнала. Конфликт `UNIQUE (reference_type, reference_id, operation)` означает, что шаг уже проведён: возвращается ранее созданный журнал (идемпотентный ответ), а не ошибка.
6. Вставка проводок с `account_version` и `balance_after`.
7. На коммите отложенный триггер повторно проверяет баланс журнала (страховка).

## 12. Финансовые инварианты

Эти инварианты проверяются тестами ([financial-invariants-testing.md](financial-invariants-testing.md)) и периодической задачей сверки в production.

| ID | Инвариант |
|---|---|
| I-01 | Для каждого журнала и каждой валюты \(\sum DEBIT = \sum CREDIT\); в журнале не меньше 2 проводок. |
| I-02 | Глобально по каждой валюте \(\sum DEBIT = \sum CREDIT\) по всем проводкам (следствие I-01, проверяется отдельно). |
| I-03 | Для каждого бизнес-счёта `account_balances.available_amount` = balance(AVAILABLE) и `reserved_amount` = balance(HOLD). |
| I-04 | Для счетов с `allow_negative = false` баланс ≥ 0 **в каждой точке истории** (проверяется по `balance_after`). |
| I-05 | `reserved_amount` = \(\sum\) `holds.amount` со статусом `ACTIVE` по счёту. |
| I-06 | Для каждого платежа `refunded_amount` ≤ `captured_amount` и `refunded_amount` = \(\sum\) успешных `refunds.amount`. |
| I-07 | Проведённые журналы и проводки не изменялись (проверка запретов и хеша содержимого, если хеш введён). |
| I-08 | Каждый бизнес-шаг проведён не более одного раза (`UNIQUE` и отсутствие дублей по ссылке). |
| I-09 | По каждому ledger-счёту с проекцией цепочка `balance_after` согласована: `balance_after(n) = balance_after(n-1) ± amount(n)`, `account_version` строго возрастает. |
| I-10 | Статус бизнес-объекта согласован с журналами: `CAPTURED` ⇔ есть ровно один `HOLD_CAPTURE`; резерв `RELEASED` ⇔ есть `HOLD_RELEASE`; `COMPLETED`-перевод ⇔ `TRANSFER` или `HOLD_CAPTURE`; `FAILED`/`CANCELLED` без резерва ⇔ журналов нет. |
| I-11 | Валюта проводки = валюта ledger-счёта = валюта бизнес-объекта. |
| I-12 | Сумма комиссии в бизнес-объекте = сумме кредита счёта дохода в его журнале и воспроизводится тарифом `fee_tariff_id`. |
