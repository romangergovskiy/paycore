# План тестирования финансовых инвариантов

Статус: **проект**. Инварианты I-01…I-12 описаны в [ledger-model.md §12](ledger-model.md#12-финансовые-инварианты), конкурентные сценарии S-01…S-20 — в [../database/concurrency.md §9](../database/concurrency.md#9-каталог-конкурентных-сценариев). Конкретные библиотеки — предложение, не решение. Зависимости на этом этапе не устанавливаются.

## 1. Стратегия

| Уровень | Что проверяет | Окружение | Когда запускается |
|---|---|---|---|
| Unit | Деньги, комиссии, машины состояний, валидация проводок | Чистый Go, без БД | Каждый коммит |
| Property-based | Свойства арифметики и последовательностей операций | Go, in-memory модель | Каждый коммит (короткий прогон), nightly (длинный) |
| Integration | Ограничения, триггеры, права, SQL-запросы, транзакционные шаблоны | Настоящий PostgreSQL той же версии, что в production (testcontainers / docker compose) | Каждый PR |
| Concurrency | S-01…S-20 под реальной конкуренцией | PostgreSQL + N горутин, `-race` | Каждый PR (короткий), nightly (много итераций) |
| Fault injection | Падения между шагами, Kafka, обрыв соединения | PostgreSQL, Kafka (позже), прокси вроде toxiproxy | Nightly / перед релизом |
| Invariant checker | Все I-xx на произвольном состоянии БД | SQL-запросы (REPEATABLE READ) | После каждого integration/concurrency-теста и по расписанию в production |
| Load (k6, ТЗ §7) | p95, повторы, ожидания блокировок, отсутствие нарушений инвариантов под нагрузкой | Стенд | Этап Production Engineering |

Главный принцип: **любой тест, который меняет деньги, заканчивается проверкой инвариантов** (общий хелпер `assertLedgerInvariants(t, db)`), а не только проверкой ожидаемого результата.

## 2. Invariant checker (переиспользуемый набор SQL)

Набор запросов, каждый из которых возвращает **пустой результат**, если инвариант выполняется. Используется в тестах, в production-задаче сверки и как отчёт Admin Dashboard.

| Инвариант | Суть запроса |
|---|---|
| I-01 | Журналы, где по какой-либо валюте \(\sum D \ne \sum C\) или проводок меньше 2 |
| I-02 | Валюты, где глобально \(\sum D \ne \sum C\) |
| I-03 | Бизнес-счета, где `account_balances` ≠ пересчёт по проводкам AVAILABLE/HOLD |
| I-04 | Проводки счетов с `allow_negative = false`, где `balance_after < 0`; системные счета с отрицательным пересчитанным балансом |
| I-05 | Счета, где `reserved_amount` ≠ \(\sum\) активных `holds` |
| I-06 | Платежи, где `refunded_amount` ≠ \(\sum\) успешных `refunds` или > `captured_amount` |
| I-08 | Дубли `(reference_type, reference_id, operation)` (на случай снятого ограничения), объекты с несколькими «финальными» журналами |
| I-09 | Разрывы цепочки: `balance_after(n) ≠ balance_after(prev) ± amount(n)`; невозрастающая `account_version` |
| I-10 | Несогласованность статусов: `CAPTURED` без `HOLD_CAPTURE`; hold `ACTIVE` с журналом `HOLD_RELEASE`; `FAILED`-перевод с журналом `TRANSFER` и т. д. |
| I-11 | Проводки, где валюта ≠ валюте счёта (на случай снятого FK) |
| I-12 | Объекты, где `fee_amount` ≠ кредиту счёта дохода в журнале или ≠ пересчёту по `fee_tariff_id` |

## 3. Unit-тесты

### 3.1. Деньги (`pkg/money`)

- Сложение и вычитание с переполнением возвращают ошибку: `MaxInt64 + 1`, `MinInt64 − 1`.
- Умножение на ставку на границе `MAX_AMOUNT × 10 000`.
- Сравнение сумм разных валют — ошибка, а не `false`.
- Парсинг строк `"100.50"` (RUB) → 10 050; `"100.5"` → 10 050; `"100.505"` → ошибка (лишний знак); `"1e3"` → ошибка; JPY `"100"` → 100.
- Сериализация в JSON — только целые числа, без float.

### 3.2. Commission Engine (таблица кейсов)

| Сумма, коп. | Тариф | Ожидаемая комиссия | Что проверяет |
|---|---|---|---|
| 100 000 | 50 bp, min 1 000, max 50 000 | 1 000 | срабатывание min |
| 500 000 | 150 bp | 7 500 | обычный расчёт |
| 30 000 000 | 50 bp, max 50 000 | 50 000 | срабатывание max |
| 333 | 150 bp, HALF_UP, min 0 | 5 | округление 4,995 → 5 |
| 100 | 50 bp, HALF_UP, min 0 | 1 | 0,5 → 1 |
| 100 | 50 bp, HALF_EVEN, min 0 | 0 | 0,5 → 0 (банковское) |
| 1 | 150 bp, min 1 000 | ≤ amount (по [Q-09](open-questions.md#q-09)) | комиссия больше суммы |
| MAX_AMOUNT | 10 000 bp | без переполнения | граница |

Также проверяется выбор тарифа: по `valid_from`/`valid_to` и персональный тариф мерчанта поверх базового.

### 3.3. Машины состояний

Табличный тест **всех пар** (статус × команда) для платежа, перевода, резерва и возврата. Разрешённые переходы ([money-flows.md §2](money-flows.md#2-машины-состояний)) дают ожидаемый новый статус. Все остальные — доменную ошибку `INVALID_STATE`. Это закрывает требование ТЗ §2.4 «нельзя вернуть средства по платежу, который не был проведён».

### 3.4. Валидация проводок (`Ledger.Post` без БД)

Отклоняются: < 2 проводок; сумма ≤ 0; несбалансированный журнал; несбалансированность в одной из двух валют при общем балансе; валюта проводки ≠ валюте счёта; дубль счёта в журнале; неизвестный `operation`. Принимается: корректный журнал из 2, 3 и 4 проводок.

### 3.5. Построители проводок (posting builders)

Для каждого сценария [money-flows.md](money-flows.md) — тест, что builder строит ровно ту таблицу проводок, что описана в документе. Это «живые» примеры: документ и тест должны совпадать.

## 4. Property-based тесты

Инструмент — на выбор: `pgregory.net/rapid` или `testing/quick` ([Q-27](open-questions.md#q-27)).

### 4.1. Свойства арифметики и комиссий

- Для любых `amount ∈ [1, MAX]` и тарифа: `min ≤ fee ≤ max` (если не действует ограничение `fee ≤ amount`); `fee ≥ 0`; результат детерминирован.
- Монотонность: `a ≤ b ⇒ fee(a) ≤ fee(b)` при одном тарифе.
- Пропорциональный возврат комиссии (D-09 B): для любого разбиения суммы платежа на возвраты \(\sum\) возвращённых комиссий = `fee_amount`, и каждая промежуточная сумма ≤ `fee_amount`.

### 4.2. Модельное тестирование (model-based / stateful)

- **Модель** — простая in-memory реализация «счета, резервы, платежи», заведомо корректная (map и целые числа, без конкурентности).
- **Генератор** — случайные последовательности команд: пополнение, перевод (с ALLOW/REVIEW/BLOCK), отмена перевода, создание, авторизация, capture, void и истечение платежа, частичный возврат, повтор команды с тем же idempotency key, сторно.
- Каждая команда применяется к **системе** (настоящие use case + PostgreSQL) и к **модели**. После каждого шага:
  - результаты совпадают (успех или ошибка того же кода);
  - балансы всех счетов совпадают с моделью;
  - invariant checker (§2) пуст.
- При падении фреймворк уменьшает (shrink) последовательность до минимальной воспроизводимой.
- Это прямо реализует ТЗ §10: «тесты, проверяющие инварианты на случайных последовательностях финансовых операций».

### 4.3. Свойство «сохранения денег»

Для любой последовательности операций без `TOPUP`, `PAYOUT` и `ADJUSTMENT` сумма обязательств перед клиентами и мерчантами плюс доход от комиссий остаётся постоянной.

## 5. Конкурентные тесты

Общий каркас:

1. Подготовить состояние (fixture) в настоящей БД.
2. Запустить N горутин, синхронизированных барьером (`sync.WaitGroup` и закрытие канала-старта), чтобы запросы действительно пересекались.
3. Собрать результаты: коды ответов, итоговые статусы.
4. Проверить ожидаемый исход сценария **и** invariant checker.
5. Повторить M раз (например, 100 в PR, 10 000 nightly), потому что гонки проявляются вероятностно.
6. Запуск с `go test -race`.

| Тест | Конфигурация | Проверка |
|---|---|---|
| S-01 | Баланс 1 000 000, 2…50 горутин по 800 000 | Ровно один успех; `available ≥ 0` |
| S-01-stress | Баланс 1 000 000, 100 горутин по случайным суммам | \(\sum\) успешных списаний ≤ 1 000 000; итоговый баланс = 1 000 000 − \(\sum\) |
| S-02 | 20 горутин с одним ключом | Один перевод, 20 одинаковых ответов |
| S-04/S-05 | capture × capture, capture × void, capture × expiry | Ровно один финальный журнал |
| S-06 | 10 горутин частичных возвратов, в сумме больше `captured` | \(\sum\) успешных ≤ `captured` |
| S-07 | Встречные переводы по кругу A→B→C→A, много горутин | Нет `40P01`; деньги сохранены |
| S-08 | Перевод × блокировка счёта | Нет проведённого перевода после момента блокировки |
| S-09 | Переводы × авторизации на одном счёте | `available ≥ 0`, I-05 |
| S-13/S-14 | 3 relay, повторная доставка | Каждое событие обработано потребителем ровно 1 раз |
| S-18 | Отмена × одобрение `ON_HOLD` | Ровно один из `HOLD_CAPTURE` / `HOLD_RELEASE` |
| S-20 | Параллельные переводы против суточного лимита | \(\sum\) ≤ лимита |

Дополнительно — тест-«детектор deadlock»: случайная смесь всех use case с проверкой, что `40P01` не возникает ни разу. Его появление — баг в порядке блокировок, а не повод для повтора.

## 6. Интеграционные тесты БД

### 6.1. Ограничения (каждое — отдельный тест «нарушить напрямую через SQL → ожидать ошибку с именем ограничения»)

- `INSERT` проводки с `amount = 0`, `amount < 0`, `amount > MAX`.
- Проводка в валюте, отличной от валюты счёта (составной FK).
- Несбалансированный журнал → ошибка на `COMMIT` (отложенный триггер). Сбалансированный журнал из нескольких операторов `INSERT` → успех.
- Журнал без проводок → ошибка на `COMMIT`.
- Дописать проводку в журнал из прошлой транзакции → ошибка.
- `UPDATE` / `DELETE` / `TRUNCATE` на `ledger_entries`, `journal_transactions`, `audit_logs` → ошибка (триггер) **и** `permission denied` для роли `paycore_app` (ТЗ §10 «Изменение проведённой проводки — запрещено»).
- `available_amount < 0` → `check_violation`.
- Повторный журнал с тем же `(reference_type, reference_id, operation, operation_seq)` → `unique_violation`.
- Двойное сторно одного журнала.
- Пересечение периодов тарифов (EXCLUDE).
- Перевод между счетами разных валют (составной FK).
- `refunded_amount > captured_amount`.
- `approved_by = created_by` в `manual_adjustments`.

### 6.2. Транзакционные шаблоны

- Каждый use case из [concurrency.md §5](../database/concurrency.md#5-шаблоны-транзакций): успешный путь создаёт ровно ожидаемые журналы, проводки, историю статусов, outbox-событие и запись idempotency — **в одном коммите**. Проверка через инъекцию ошибки на последнем шаге: после неё в БД нет ни одного следа операции.
- Отказ из-за бизнес-правила сохраняет объект `FAILED` без проводок.
- Retry-обёртка: искусственный `40001` на первой попытке (например, конфликтующая транзакция в REPEATABLE READ) → успех на второй, эффект один.

### 6.3. Восстановление баланса

Заполнить БД случайными операциями (из §4.2) → `TRUNCATE` проекции в тестовой БД (в тестовой роли) → пересчитать из ledger → совпадение с исходной проекцией (ТЗ §2.3 «восстановление баланса по истории»).

## 7. Fault injection

| Сбой | Ожидание |
|---|---|
| Kill процесса после `COMMIT`, до ответа клиенту | Повтор с ключом возвращает результат, эффект один |
| Обрыв соединения во время `COMMIT` (прокси) | Исход определяется повтором с тем же ключом |
| Kafka недоступна N минут | Outbox растёт, после восстановления все события доставлены (ТЗ §10) |
| Kill relay после публикации, до `UPDATE published_at` | Дубль события, потребитель отбрасывает его через inbox |
| Kill между ТХ1 и ТХ2 внешнего платежа | Recovery-задача доводит платёж до конца ровно один раз |
| `lock_timeout` из-за длинной чужой транзакции | `503` + `Retry-After`, без частичных эффектов |

## 8. Критерии готовности (Definition of Done) для финансового ядра

1. Все сценарии [money-flows.md](money-flows.md) покрыты тестами builders (§3.5) и интеграционными тестами.
2. Все S-01…S-20 зелёные на 10 000 итераций nightly.
3. Модельный тест (§4.2) проходит не менее 1 000 последовательностей по 200 команд.
4. Invariant checker пуст после каждого теста и после нагрузочного прогона.
5. Сценарии из таблицы ТЗ §10 сопоставлены с тестами явно (трассировка ниже).

| Сценарий ТЗ §10 | Тест |
|---|---|
| Перевод 1 000 ₽ | §3.5 builder TRANSFER + §6.2 |
| Перевод при недостатке средств | §6.2 (FAILED без проводок) |
| Два параллельных перевода по 8 000 ₽ | S-01 |
| Повтор запроса с тем же ключом | S-02, S-10 |
