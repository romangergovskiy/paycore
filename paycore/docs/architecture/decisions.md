# Архитектурные решения MVP

Статус: **принято для MVP** (этап 2). Документ — единый реестр окончательных решений. Всё, что здесь не решено, лежит в [open-questions.md](open-questions.md). После старта реализации решения переносятся в ADR (`docs/adr/`, ТЗ §11) без изменения сути.

Идентификаторы D-01…D-19 сохранены с этапа 1, чтобы не ломать ссылки. Решения D-20 и далее появились на этапе 2. У каждого решения указаны выбранный вариант, альтернативы и краткое обоснование.

---

## 1. Скоуп и границы MVP

### D-20
**Скоуп MVP.**
- **Входит:** клиенты с виртуальными счетами; магазины (мерчанты); переводы между клиентами и между своими счетами; оплата покупок через checkout; возвраты (полные и частичные); комиссии платформы; выплаты магазинам; админ-панель; публичный REST API; история операций и финансовые отчёты; лимиты; аудит.
- **Не входит:** реальные карты и деньги; внешние платёжные провайдеры; вывод средств клиентом за пределы платформы (деньги клиента выходят только через платежи и переводы); чарджбэки; FX; овердрафт; KYC/AML; Kafka как обязательный компонент; fraud-проверка с ручным разбором (`REVIEW`); сверка с внешним реестром провайдера.
- **Что подготовлено для следующих фаз:** проектные описания `REVIEW`/`ON_HOLD`, внешнего провайдера, счетов 1200/1300/2300/2900 и т. п. сохранены, но помечены как «после MVP».
- **Чего не заявляем:** соответствия PCI DSS, банковским требованиям, KYC/AML.
- *Обоснование:* формулировка концепции этапа 2. Ядро (ledger, платежи, переводы) должно быть корректным без внешней инфраструктуры.

### D-15
**Источник виртуальных денег — модуль-симулятор.**
- **Выбрано:** отдельный модуль `simulator` с операцией `SIM_TOPUP`: Дт 1100 «Внешний источник виртуальных средств (симулятор)» / Кт счёт клиента. Выплата магазину выводит деньги «во внешний мир» симулятора: Дт счёт магазина / Кт 1100.
- **Альтернатива:** демо-эмиссия через капитал (Дт 3100 / Кт 2100). Отклонена: «капитал» уходит в минус, и экономического смысла нет.
- *Обоснование:* с точки зрения ledger симулятор — такой же внешний контрагент, как банк. Код ledger, платежей и переводов не знает о симуляции. Это отделяет симуляцию от «банковских» операций ([money-flows.md §3](money-flows.md#3-симулятор-источник-и-сток-виртуальных-денег)).

### D-25
**Выплаты магазинам — синхронная операция симулятора.**
- **Выбрано:** магазин (роль OWNER) запрашивает выплату. В одной транзакции проводится журнал `PAYOUT`: Дт MA:2200 / Кт 1100. Статус выплаты сразу `COMPLETED` или `FAILED`. Комиссии за выплату нет. Расписания нет.
- **Альтернатива:** трёхшаговая асинхронная выплата (`PAYOUT_INIT` → `SETTLE`/`FAIL` через 2210). Сохранена как дизайн «после MVP».
- *Обоснование:* без внешнего банка промежуточному состоянию нечего ждать.

## 2. Финансовая модель

### D-01
**Резерв — проводка в ledger.**
- **Выбрано:** `HOLD_PLACE` (Дт 2100 / Кт 2110). `reserved_amount` полностью восстанавливается из ledger.
- **Альтернатива:** memo-резерв вне ledger (только строка `holds`).
- *Обоснование:* ТЗ §2.3 «поддержка резервирования» и «восстановление баланса по истории».

### D-11
**Владелец бизнес-счёта.**
- **Выбрано:** `user_id` / `merchant_id` с FK и `CHECK num_nonnulls = 1`.
- **Альтернатива:** полиморфная пара `owner_type/owner_id`. Отклонена: нет FK-целостности.

### D-30
**Валюты MVP: RUB и USD** (как в примере ТЗ §2.2), `minor_units = 2`.
- Один бизнес-счёт имеет одну валюту, FX нет.
- Справочник `currencies` позволяет добавить валюту без изменения кода.

### D-35
**Максимальная сумма.**
- Технический предел — `MAX_AMOUNT = 10^14` минорных единиц, задан CHECK в проводках. При таком пределе `amount × rate_bp` не переполняет `int64`.
- Бизнес-ограничения задаются лимитами ([D-24](#d-24)).

### D-17
**Комиссии: целочисленная формула, ставка в bp, округление `HALF_UP`.**
- Режим округления хранится в тарифе.
- **Альтернативы:** `HALF_EVEN`, `UP`; ставка в ppm.

### D-08
**Комиссия за платёж удерживается с магазина при capture.**
- Комиссия рассчитывается **в транзакции capture** по тарифу, действующему на момент capture. Результат сохраняется в `fee_amount` и `fee_tariff_id`.
- **Альтернативы:** фиксировать комиссию при авторизации; списывать отдельно при выплате; комиссию платит покупатель.
- *Обоснование:* расчёт и проведение в одной транзакции исключают «устаревшую» комиссию. Это прямое требование этапа 2.

### D-09
**Комиссия при возврате не возвращается.**
- Покупатель получает полную сумму возврата, а комиссия остаётся доходом платформы.
- **Альтернатива** — пропорциональный возврат через контр-счёт 4900 — оставлена как дизайн «после MVP».

### D-10
**Возврат требует достаточного доступного остатка магазина.**
- Если `MA.available < refund.amount`, возврат не проводится. Он сохраняется со статусом `FAILED`, код `MERCHANT_INSUFFICIENT_FUNDS`, HTTP `422`. Платёж не меняется.
- **Альтернативы:** задолженность магазина (счёт 1300); rolling reserve (2210).
- *Важное следствие:* после полного возврата магазин теряет комиссию. Поэтому последний возврат может не пройти, пока у магазина нет других поступлений (пример — [money-flows.md §7](money-flows.md#7-возвраты)).

### D-27
**Комиссия за перевод.**
- Платит отправитель **сверх** суммы перевода, получатель получает ровно `amount`.
- Переводы между своими счетами — тариф 0.
- min и max задаются в тарифе для каждой валюты.
- Для платежа: если по действующему тарифу `fee >= amount`, создание платежа отклоняется (`AMOUNT_TOO_SMALL`). Если тариф изменился между созданием и capture, комиссия при capture ограничивается суммой платежа (`CHECK fee_amount <= amount`).
- **Альтернатива:** комиссия из суммы перевода.

### D-06
**Журнал создаётся только проведённым.**
- `status = 'POSTED'`, отмена — новым журналом.
- **Альтернатива:** жизненный цикл `PENDING → POSTED` у журнала. Отклонена: противоречит неизменяемости.

### D-16
**Running balance в проводках.**
- Для счетов клиентов и магазинов проводка хранит `account_version` и `balance_after`; действует `UNIQUE (ledger_account_id, account_version)`.
- У системных счетов (бакеты, [D-02](#d-02)) этих полей нет. Их проверяют CHECK на бакетах и инвариант I-03.

## 3. Балансы и системные счета

### D-02
**Синхронная проекция есть у всех ledger-счетов. У системных она разбита на бакеты.** *(Пересмотрено на этапе 2. Прежнее решение «без проекции, контроль сверкой» отменено.)*
- Счета клиентов и магазинов — одна строка `account_balances` с `CHECK (available_amount >= 0 AND reserved_amount >= 0)`.
- Системные счета — `ledger.system_balance_buckets(ledger_account_id, bucket_no, balance)`, по `bucket_count` строк на счёт.
  - Для счетов с `allow_negative = false` каждый бакет имеет `CHECK (balance >= 0)`. Значит, и сумма неотрицательна **в момент проведения**.
  - **Увеличение** остатка обновляет один бакет, выбранный по хешу id журнала: конкуренция снижается в `bucket_count` раз.
  - **Уменьшение** блокирует все бакеты счёта по порядку, проверяет сумму и распределяет списание. Уменьшение редкое: выплаты, корректировки, сторно.
  - Текущий баланс — `SUM(balance)` по бакетам.
- Таблица по каждому системному счёту — [chart-of-accounts.md §3](chart-of-accounts.md#3-системные-счета-остаток-контроль-проекция).
- **Альтернативы:**
  - одна строка на системный счёт — горячая строка, все платежи сериализуются;
  - без проекции с контролем сверкой — отклонено требованием этапа 2;
  - асинхронная агрегация — отрицательный остаток не ловится вовремя.

## 4. Целостность и неизменяемость ledger

### D-03
**Единственный путь записи в ledger — функции PostgreSQL `SECURITY DEFINER`.** *(Пересмотрено: защита через `xmin` убрана.)*
- `ledger.post_journal(...)` в одном вызове:
  - проверяет журнал: ≥ 2 проводок, суммы > 0, \(\sum D = \sum C\) по каждой валюте, валюты счетов, статусы счетов, допустимую операцию;
  - вставляет журнал (`POSTED`) и **все** проводки;
  - обновляет проекции и бакеты;
  - меняет статус резерва (`holds`), если операция резервная.
- `ledger.lock_account_balances(uuid[])` блокирует проекции в отсортированном порядке и возвращает остатки.
- `ledger.open_ledger_accounts(...)` создаёт ledger-счета и строку проекции при открытии счёта.
- Роль приложения `paycore_app` **не имеет** `INSERT/UPDATE/DELETE/TRUNCATE` на `journal_transactions`, `ledger_entries`, `account_balances`, `system_balance_buckets`, `holds`. Ей выдан только `EXECUTE` на эти функции и `SELECT`.
- Вторая линия защиты: триггеры `BEFORE UPDATE/DELETE/TRUNCATE` (запрет для всех, включая владельца, пока триггер не отключён) и отложенный constraint trigger сбалансированности (страховка для сидов и миграций).
- Go-сервис `Ledger.Post` остаётся. Он строит и валидирует журнал в домене и вызывает функцию.
- **Альтернативы:**
  - Go + отложенные триггеры + `xmin` — отклонено: хрупко, не защищает от «дописывания» без `xmin`;
  - только Go — отклонено: ручной SQL обходит проверки.
- *Обоснование:* одна понятная точка входа. Запреты обеспечены правами, а не соглашением. Журнал и проводки атомарно создаются одним вызовом, поэтому «дописать» проводку в проведённый журнал физически нечем ([data-integrity.md §4](../database/data-integrity.md#4-неизменяемость-ledger)).

### D-13
**Перечисления — `TEXT + CHECK`.** Справочные таблицы используются для плана счетов и ролей. Альтернатива — `ENUM`.

### D-14
**Идентификаторы — UUIDv7, генерируются в Go.** Альтернативы — UUIDv4 или `BIGINT`.

### D-18
**Схема PostgreSQL на каждый модуль.**

### D-12
**FK между модулями** разрешены по явному списку ([er-diagram.md §7](../database/er-diagram.md#7-межмодульные-связи)).

### D-19
**Бизнес-отказы сохраняются.** Объект получает статус `FAILED` и код причины. Ошибки формата запроса не сохраняются.

## 5. Платежи, переводы, резервы

### D-21
**Жизненный цикл платежа в MVP: `PENDING` не используется.**
- Статусы MVP: `CREATED`, `AUTHORIZED`, `CAPTURED`, `PARTIALLY_REFUNDED`, `REFUNDED`, `FAILED`, `CANCELLED`.
- Базовая цепочка этапа 2 `CREATED → PENDING → AUTHORIZED` и переход `PENDING → FAILED` в MVP выполняются **атомарно в одной транзакции** подтверждения checkout. Поэтому промежуточный `PENDING` никто не может наблюдать, и он не хранится: `CREATED → AUTHORIZED` или `CREATED → FAILED`.
- `PENDING` вводится миграцией вместе с асинхронным шагом (fraud `REVIEW`, внешний провайдер).
- Добавлен переход `CREATED → CANCELLED`: магазин отменил платёж или checkout истёк. Без него неоплаченные платежи висели бы вечно.
- **Альтернатива:** хранить `PENDING` в MVP для «полноты» — отклонено как лишнее состояние.
- Машина состояний — [money-flows.md §2.1](money-flows.md#21-платёж).

### D-22
**Checkout: магазин не может выбрать счёт покупателя.**
- Магазин (API-ключ) создаёт платёж без счёта покупателя и получает `checkout_url` с одноразовым токеном.
- Покупатель, аутентифицированный своим токеном, открывает checkout, выбирает **свой** счёт и подтверждает. В этот момент происходит авторизация (резерв).
- Capture и void выполняет магазин. Покупатель не может отменить авторизацию в MVP.
- Это заменяет пример ТЗ §5 с `account_id` в теле `POST /payments`.
- После неудачного подтверждения (`FAILED`) магазин создаёт новый платёж.

### D-36
**Одна авторизация — один capture на полную сумму.** Частичного и многократного capture в MVP нет.

### D-32
**Сроки (значения по умолчанию, конфигурируются).**
- Checkout-сессия живёт 30 минут, затем `CREATED → CANCELLED (CHECKOUT_EXPIRED)`.
- Авторизация живёт 7 суток, затем `AUTHORIZED → CANCELLED (AUTH_EXPIRED)`, резерв → `EXPIRED`.

### D-05
**Переводы в MVP проводятся синхронно** (`COMPLETED` или `FAILED`).
- Путь через резерв (`ON_HOLD` при fraud `REVIEW`) отложен вместе с fraud-движком ([D-20](#d-20)).
- Поэтому «отмена перевода до проведения» (ТЗ §2.5) в MVP **неприменима**: перевод проводится в момент запроса. Это осознанное отклонение от ТЗ ([open-questions.md, Q-16](open-questions.md#q-16)).
- **Альтернатива:** всегда через резерв с окном отмены.

### D-24
**Лимиты: счётчик на пользователя, блокировка строки счётчика.**
- В MVP два вида лимитов:
  - максимум одной операции — без счётчика;
  - суточный лимит исходящих средств пользователя в валюте. В него входят переводы другим людям и авторизации платежей, без комиссий; переводы между своими счетами не входят. Отдельный суточный лимит — на тестовые пополнения.
- Счётчик `limit_counters(user_id, currency, limit_type, period_start)` блокируется `FOR UPDATE` на уровне **L4** общего порядка (до проекций балансов на L5) ([concurrency.md §3](../database/concurrency.md#3-единый-порядок-захвата-блокировок)).
- Void и истечение авторизации возвращают лимит, только если период тот же. Возврат лимит не возвращает. Период — сутки UTC.
- **Альтернатива:** SERIALIZABLE для проверки лимита. Отклонена: менее предсказуемо.
- Значения лимитов — [open-questions.md, Q-12](open-questions.md#q-12).

### D-26
**Блокировка счёта (`BLOCKED`).**
- Запрещены все операции, инициированные пользователем или магазином: списания, зачисления переводов, авторизации, capture, выплаты.
- Разрешены операции, возвращающие владельцу его же деньги: `HOLD_RELEASE` (void, истечение), `REFUND` на заблокированный счёт покупателя.
- Таблица `account_restrictions` (частичные ограничения) в MVP не используется, только статус.
- **Альтернатива:** полный запрет, включая возвраты.

### D-28
**Закрытие счёта** возможно только при нулевом доступном остатке и без активных резервов. Иначе `409 ACCOUNT_NOT_EMPTY`.

### D-37
**Владелец таблицы `holds` — модуль Ledger.** Изменяется только функцией `ledger.post_journal`.

## 6. Конкурентность и надёжность

### D-04
**Изоляция:**
- **денежные операции** — READ COMMITTED плюс явные блокировки в едином порядке L1…L8, условные `UPDATE` и CHECK;
- **отчёты и проверки инвариантов** — REPEATABLE READ READ ONLY;
- **retry** на `40001`/`40P01`/`55P03` (последний — ограниченно).

Альтернативы — SERIALIZABLE везде или оптимистичные версии.

### D-07
**Идемпотентность в два уровня.**
- **HTTP-ключ** записывается в **той же** транзакции, что и бизнес-эффект: сначала `INSERT … IN_PROGRESS`, в конце — `UPDATE … COMPLETED`.
- Второй одновременный запрос с тем же ключом ждёт на уникальном индексе (не дольше `lock_timeout`):
  - если первый закоммитился — получает сохранённый ответ;
  - если первый откатился — выполняет операцию сам.
- Другое тело с тем же ключом → `409 IDEMPOTENCY_KEY_REUSED`.
- Срок хранения ключа — 24 часа.
- Область ключа — пользователь (`user:<id>`) или магазин (`merchant:<id>`, а не API-ключ, потому что ключи ротируются).
- Бизнес-`UNIQUE` (платежи, переводы, возвраты, ledger) действует бессрочно.
- Подробный алгоритм — [concurrency.md §4](../database/concurrency.md#4-идемпотентность-http).
- **Альтернатива:** двухфазный протокол с коммитом `IN_PROGRESS` и lease. Оставлен для будущих многошаговых операций с внешними вызовами.

### D-23
**Transactional outbox с lease. Kafka в MVP не обязательна.**
- Событие пишется в `outbox_events` в бизнес-транзакции.
- Relay:
  - захватывает пачку короткой транзакцией (`processing_until`, `lease_owner`, `FOR UPDATE SKIP LOCKED`);
  - публикует **вне** транзакции;
  - подтверждает публикацию отдельной короткой транзакцией с проверкой владельца lease;
  - после падения просроченные lease перехватываются.
- Порядок — внутри агрегата по `seq`. Доставка at-least-once, потребители идемпотентны через `inbox_messages`.
- В MVP «публикация» — это вызов внутренних обработчиков (уведомления, создание webhook-доставок) фоновым worker. Kafka подключается позже как ещё один publisher.
- Подробно — [concurrency.md §7](../database/concurrency.md#7-transactional-outbox-и-inbox).

### D-29
**Учёт ведётся в UTC.** `accounting_date` и границы суток для лимитов и отчётов — UTC. Отображение — в часовом поясе пользователя.

## 7. Доступ и контроль

### D-31
**Ручные корректировки — maker-checker.**
- Заявку создаёт OPERATOR, утверждает ADMIN, причём это обязательно разные люди (`approved_by <> created_by`). Обоснование и ссылка на инцидент обязательны.
- Проводит корректировку сервис через `ledger.post_journal`. У ADMIN нет прямого способа изменить баланс (ТЗ §2.1).
- Порога суммы для второго утверждения в MVP нет.

### D-33
**Роли БД:** `paycore_owner` (миграции), `paycore_ledger` (NOLOGIN, владелец ledger-функций), `paycore_app`, `paycore_readonly`. Права перечислены в [data-integrity.md §6](../database/data-integrity.md#6-роли-и-права-бд).

### D-34
**Инфраструктурные параметры MVP.**
- PostgreSQL 16 или новее.
- Партиционирования ledger нет (индексы, BRIN, снапшоты).
- Чарджбэков нет.

## 8. Сводка «было → стало» (этап 1 → этап 2)

| Тема | Этап 1 | Этап 2 |
|---|---|---|
| Системные счета | Без синхронной проекции, контроль сверкой | Бакетная синхронная проекция с CHECK ≥ 0 (D-02) |
| Защита ledger | Go + deferred trigger + `xmin` | `SECURITY DEFINER`-функции как единственный путь + права + триггеры (D-03) |
| Outbox relay | Транзакция удерживается во время публикации | Lease, публикация вне транзакции (D-23) |
| Идемпотентность | Протокол в общих чертах | Пошаговый алгоритм для всех случаев (D-07) |
| Платёж | `PENDING` хранится, магазин передаёт счёт | Без `PENDING` в MVP, checkout (D-21, D-22) |
| Возврат | Варианты A/B/C | Только при достаточном остатке, комиссия не возвращается (D-09, D-10) |
| Переводы | ALLOW / REVIEW | Только синхронно (D-05) |
| Лимиты | Вопрос | Счётчик, блокировка L4 (D-24) |
| Порядок блокировок | L1…L6 | L1…L8 (добавлены лимиты и бакеты) |
| Внешний провайдер, fraud, сверка | Частично в MVP | После MVP (D-20) |
